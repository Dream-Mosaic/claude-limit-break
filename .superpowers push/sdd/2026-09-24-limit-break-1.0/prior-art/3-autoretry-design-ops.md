## DESIGN-NOTES.md — decisions and reversals (read in full)

Source: `claude-auto-retry/DESIGN-NOTES.md`. Dated 2026-06, against Claude Code v2.1.195 (decompiled).

**Core framing (line 9-17, doc's own words):** the whole tool scrapes a "human-facing render" (`tmux capture-pane` + string match). Every false positive/negative traces to that layer choice. This is their stated central regret.

**Ground truth they derived from the binary (line 19-41):**
- Two renders for the same error code, opposite meaning: colon form `API Error: <code> <body>` = terminal/exhausted; parens form `API Error (<code> …) · Retrying in 5s · attempt 3/10` = Claude's own internal retry still in flight. Acting on the parens form double-drives a retry Claude is already doing. [done] in their code: colon-form required, retry-suffix suppressed.
- Retryable set: `500, 504, 529`, edge `502/503` (bodyless, e.g. Cloudflare/envoy `503 no healthy upstream`). `429 rate_limit_error` on a subscription is NOT treated as transient-retryable — it's the hours-scale usage/session limit, routed to their usage-wait path, not the overload backoff. Never retry `400/401/402/403/404/413`.
- API-429 renders with **no 3-digit code in the slot** (`API Error: Server is temporarily limiting requests (not your usage limit) · Rate limited`) — a code-keyed regex misses it entirely, so they added a phrase-pattern fallback.
- 529 is *global* capacity, not per-key — naive fixed backoff resynchronizes every client into the same overload window, hence full-jitter recommendation (§3, proposed not shipped — default jitter is proportional `base × (1±pct%)`, `jitterMode: full` is a proposal, not implemented per the doc's own "Proposed" language).
- Streaming caveat: an error after 200 OK (SSE `error` event) bypasses HTTP status entirely; explicitly *not* special-cased ("low observed frequency").

**§1 — REVERSED/superseded design, now [done] as of v0.4.0 — the single biggest rationale flip in the doc.** Original plan: resolve session via `/proc/<pid>/environ` → `CLAUDE_CODE_SESSION_ID` on the main claude PID. Built, then found wrong in practice: the main PID's environ carries `CLAUDE_CONFIG_DIR` but NOT the session id — that var is only injected into claude's *child* processes. Fix actually shipped: the launcher stamps `CLAUDE_AUTO_RETRY_PANE` onto claude's own env; a `StopFailure` hook (a claude child process, so it inherits that var) writes a pane-keyed marker file under `~/.claude-auto-retry/events/` on transient-overload error types only (matcher `overloaded|server_error`; `rate_limit` deliberately excluded — see events.js). The monitor polls for its own pane's marker each tick; first marker latches `eventMode` and disables the scraper for that session for good. Edge-triggered (one backoff-then-send per failure). Residual caveat they document: a recycled tmux pane id could replay a stale marker — bounded by `eventMaxAgeSeconds` (default 120) + consume-on-read.

This matters for us: **`StopFailure` is observability-only** — no prompt injection, no exit-code action from Claude Code itself; it can only be used to *detect*, never to *actuate*. They pair a passive hook-writer with an active daemon reader. Verified against the decompiled v2.1.195 binary: `StopFailure` is a real event (`executeStopFailureHooks`, distinct from plain `Stop`), with 9 typed `error` values in the matcher: `overloaded, server_error, rate_limit, authentication_failed, oauth_org_not_allowed, billing_error, invalid_request, model_not_found, max_output_tokens`. Hook payload: `{hook_event_name: "StopFailure", error, error_details, last_assistant_message}` plus the standard envelope (`session_id, transcript_path, cwd`).

**§2 — JSONL-tail fallback (proposed, not marked [done]).** If hooks aren't installed: tail `$CLAUDE_CONFIG_DIR/projects/<cwd-slug>/<sessionId>.jsonl`, fire only on `type:"assistant"` records with the structured field **`isApiErrorMessage: true`** on the *last* record — explicitly never substring-grep the body, because the body can contain `overloaded_error`/`API Error` as ordinary conversation content, "reproduc[ing] the original bug." This is exactly our situation: Limit Buster already watches the transcript JSONL, so this is directly relevant prior art for a trigger field to look for, even though claude-auto-retry itself hasn't built it. Pane→transcript mapping they verified: `pane → claude PID → /proc/<pid>/environ → $CLAUDE_CONFIG_DIR + CLAUDE_CODE_SESSION_ID` (filename == sessionId); normal completion is `message.stop_reason ∈ {end_turn, tool_use, stop_sequence}`, error path writes no successful assistant message.

**§5 — operational lifecycle pain, directly observed, not theoretical.** Quote: "This session accumulated **four** detached `monitor.js` processes across launches, some watching reused pane IDs — diagnosing required `pgrep`/`kill` by hand." Drove: (a) no `ps`/`stop` subcommands existed yet when this was written (gap noted, later shipped per README's CLI Commands — `status` exists but note the doc calls out missing `ps`/`stop` explicitly as a gap); (b) pane-ID reuse risk — tmux recycles pane ids, a monitor whose pane closed and got reassigned could `send-keys` into the wrong (new) pane; mitigation proposed: re-verify the watched PID still maps to the target pane every tick, in addition to the PID-liveness self-exit; (c) monitor self-exits after 10 consecutive capture errors (~50s) — proposed tightening; (d) larger idea (not built): single supervisor process with a pane→PID registry replacing per-launch detached forks, "eliminates pile-ups structurally."

**§6 — send-keys can corrupt a half-typed prompt.** The foreground-process check does NOT catch the user mid-typing in Claude's own input box; `send-keys` would inject text there. Documented as an accepted gap; proposed cheap guard (confirm input box is empty by checking the captured prompt line is just the glyph) is called "imperfect via scraping; clean via the §1 architecture."

**§7 — 2-tick debounce, proposed not built.** A capture taken mid-render could transiently show the colon form before the "retrying" suffix paints, i.e. a race within their own scrape. Proposed N-consecutive-captures confirmation before first send. Says "worth it if §1 isn't adopted" — i.e. downgraded in priority once the hook-based trigger shipped.

**§8 — print-mode parity, proposed not built.** `launchPrintMode` (their `-p` path) retries on usage limits but NOT on overload as of doc-writing; a `-p` run hitting sustained 529 exits non-zero with `API Error:` on stderr. Proposed: apply the same overload backoff logic there by inspecting exit code + stderr.

**§9 — golden-capture test corpus, proposed not built.** Current tests (at doc-writing time) use synthetic strings, not real captured panes. Proposed capturing real panes per error type as golden files for regression-safety against Claude Code render drift.

**Residual accepted false positive (explicitly documented, not silently ignored):** because detection string-matches the render, a live tail containing literal `API Error: <code>` in prose/code (e.g. editing this repo, or documenting Claude's own error handling) will fire. Explicitly stated as unavoidable while string-matching; escape hatch is `overload.enabled: false`. They frame §1/§2 (structured-field triggers) as the actual fix for this whole class, not a scraper tweak.

## README.md / llms.txt — user promise, install, limitations

Source: `claude-auto-retry/README.md`.

**Core promise (line 5-8):** "When Claude Code shows *5-hour limit reached - resets 3pm*, this tool waits for the reset and sends 'continue' automatically. You come back to find your work done." Tagline: "No dependencies. No workflow change. Just install and forget."

**Note (line 13):** as of Aug 2026 doc claims Claude Desktop app got a native "Auto-continue when limits reset" checkbox; CLI still lacks it, framed as the reason the tool exists.

**Install flow (line 31-34):**
```
npm i -g claude-auto-retry
claude-auto-retry install
```
`install` = inject a shell function into `.bashrc`/`.zshrc` (fish: manual, instructions printed) + auto-install tmux via apt/dnf/brew/pacman/apk if missing (requires sudo for system package managers, per Known Limitations #3). The shell function intercepts your normal `claude` invocation: if already in tmux, starts a background monitor + launches claude with full TUI; if not in tmux, transparently creates a tmux session, launches claude+monitor inside it, and attaches — "looks the same to you."

**How it works (line 46-69):** monitor polls the tmux pane every 5s (default), detects rate-limit text, parses reset time (IANA timezone + half-hour offsets + iterative DST correction), waits until reset+60s margin, re-verifies claude is still the foreground process, sends "continue" via `tmux send-keys`.

**Why tmux (line 71-73), their stated rationale:** survives SSH drop / terminal close / laptop sleep because tmux itself keeps running server-side; reattach later and the work is done. This is the core architectural bet the whole tool is built on — persistence via a detached multiplexer, not via anything Claude Code itself provides.

**Feature list (line 75-92) beyond core retry — worth reading in full for scope, not just headline:** overload backoff (5xx/429/529, separate exponential-backoff path from usage-limit path); safeguard/AUP-false-positive retry (bounded, since a sticky flag means real block); interrupted-stream resume (laptop sleep / dropped connection mid-turn); near-limit wrap-up nudge (~95%-of-window checkpoint message that ends the turn early with no banner — undocumented Claude Code server-side behavior they reverse-engineered, "feature-flagged, not a setting"); tmux status-bar indicator; `--print` mode retry; config validation with safe-default fallback (never crashes on bad config).

**`/rate-limit-options` menu handling (line 114-124):** when Claude Code shows the interactive "1. Upgrade your plan / 2. Stop and wait" menu, the tool locates the cursor position and selects "Stop and wait" — explicitly "refuses to press Enter if the layout is unreadable" (fails safe rather than guessing a menu position and risking hitting "Upgrade").

**Chrome-aware detection (line 166-176), a nuance worth stealing conceptually:** the scraper skips Claude Code's own UI furniture (input box, footer, key hints, todo/task widget, status spinner, `/usage-credits` hint) before pattern-matching the "live bottom" of the pane, so a banner pushed up-screen by a tall task list still registers, while a banner merely *quoted* in scrollback with real output below it does not. User-supplied `customPatterns`, by contrast, match the **raw** last-N lines (not chrome-skipped) — documented tradeoff: "You own the false-positive tradeoff for your regexes; the built-in detection keeps the chrome-aware discipline."

**Env var escape hatches (line 206-232):**
- `CLAUDE_AUTO_RETRY_LAUNCH_WRAPPER` — prefix command prepended to each interactive launch (e.g. `caffeinate -i` on macOS to prevent sleep). Generic, not macOS-specific.
- `CLAUDE_AUTO_RETRY_KEEP_SHELL=1` — pre-0.7 behavior, keep a shell alive in the pane after claude exits (as of 0.7+ default, a clean exit now tears the tmux session down with it; a crash — non-zero exit — falls through to a login shell so scrollback survives for inspection). This is a stated behavior REVERSAL between versions.
- `CLAUDE_AUTO_RETRY_NO_TMUX=1` — never create a tmux session (for nested-multiplexer users, e.g. inside Zellij/screen); documented consequence: "this disables auto-retry for the run" since the monitor needs a pane to watch.

**Secret-handling detail worth noting (line 234-239):** full shell env reaches claude-in-tmux via a `0600`-permission snapshot file under `~/.claude-auto-retry/tmp/` that only the launcher reads and immediately deletes — explicit rationale given: nothing about the environment (names or values) ever appears on a `tmux` command line, so secrets can't leak via `/proc/<pid>/cmdline` (which is world-readable on Linux). This is a specific, named threat model they designed against.

**Known Limitations (line 688-694), their own words:**
1. Retry message sent as plain text; if Claude was mid-confirmation/special-input-state it "may not interpret it as a continuation."
2. Node version lock — launcher path resolved at install time; switching Node via nvm requires re-running `install`.
3. tmux required; auto-installs but needs sudo for system package managers.

**Uninstall (line 679-686):**
```
claude-auto-retry uninstall
npm uninstall -g claude-auto-retry
```
Stated scope: "removes the shell function from your rc files. tmux is left installed." So uninstall is rc-file-scoped only; no mention of removing `~/.claude-auto-retry/` state dir, logs, or the installed `StopFailure` hook (uninstall-hook is a *separate* explicit command, not rolled into `uninstall`) — a user who ran `install-hook` and later runs plain `uninstall` still has the hook wired into `settings.json` per this doc's own text (not verified further than the README's own command list; would need reading `bin/cli.js` to confirm `uninstall` doesn't also strip hooks — flagging as to-verify, not yet checked).

**Platform support (line 627-639):** Windows explicitly NOT supported natively — "the tool drives a tmux pane, which Windows does not have. Use WSL2." This is a full platform gap for a Windows-native audience (relevant since Limit Buster is a VS Code extension, cross-platform by nature).

**FAQ safety answers (line 770-789), their own claims:** "Can it accidentally type into the wrong program? — monitor verifies foreground process is node or claude before sending keys... skips the retry" if you've switched to vim/bash/anything else. "What if I continue manually before retry fires? — monitor checks if rate limit is still visible before sending; resets and keeps watching" if already handled.

## Config: side-by-side with ours

Source: `claude-auto-retry/src/config.js` (244 lines) + `test/config.test.js` (79 lines, 12 tests) vs our `src/config.ts` + `package.json` `contributes.configuration`.

**Shape difference, most important structural fact:** their config is a flat-ish JS object tree loaded from a user-authored `~/.claude-auto-retry.json` (global, not per-workspace, not IDE-integrated) with **4 nested sub-blocks** (`overload`, `safeguard`, `streamInterrupted`, `nearLimitWrapUp`), one per failure family, each independently enable/disable-able and independently validated. Ours is a **flat, single-namespace** `Settings` interface sourced from VS Code's own settings system (`ConfigSource.get`), each key individually scoped (`window` vs `machine`) via `package.json`'s `contributes.configuration` — no nested blocks, and no per-failure-family enable switches (we have one `enabled` toggle for the whole extension, not per detector).

**Validation philosophy — same instinct, same idiom, independently converged:** both use the pattern "coerce to expected type/range, else silently fall back to a named default; never throw, never propagate NaN/undefined." Their `validNumber(val, min, fallback)` and `clamp(val, lo, hi, fallback)` (config.js:132-139) are structurally identical in intent to our `atLeast(value, floor, fallback)` and `oneOf(list, value, fallback)` (config.ts:29-33). Their test suite (config.test.js) explicitly asserts: invalid JSON → full defaults (line 33-43), string where number expected → falls back per-field not whole-object (line 44-55), negative numbers rejected per-field (line 67-78), regex-invalid `customPatterns` entries filtered out individually while valid ones survive (line 56-66, `validPatterns` at config.js:173-181 tries `new RegExp(p)` and drops any that throw — a detail we should check we replicate for anything regex-shaped, though skim of config.ts shows we have no user-supplied-regex surface at all, so this may be moot for us).

**Their shallow-merge-per-block detail (config.js:141-144, explicit comment):** a partial user-supplied `overload: {...}` block is merged key-by-key against `DEFAULT_OVERLOAD`, not replaced wholesale — so a user who sets only `overload.enabled: false` keeps every other overload default. Comment explicitly calls out that a naive spread would otherwise blow away undocumented keys. Not directly applicable to us since we have no nested user-authored config blocks, but the principle (partial override should never silently drop sibling defaults) is worth keeping in mind if we ever add a compound setting.

## Reconcile, launchd/systemd, and what "self-healing" means here

Source: `claude-auto-retry/src/reconcile.js` (563 lines), `systemd/claude-auto-retry-reconcile.{service,timer}`, `launchd/com.claude-auto-retry.reconcile.plist`, `test/reconcile.test.js` (57 tests).

**What reconcile is for, in the doc's own framing (reconcile.js:1-10):** monitors are detached Node processes with **no supervising service**. If one is killed, crashes, or a `claude` session is started outside their shell wrapper, that session becomes permanently unmonitored — coverage only exists for *new* wrapper-launched sessions. `reconcile` restores full coverage by re-deriving ground truth from live `tmux list-panes` + `ps` state and arming a monitor for every live claude pane that lacks one. This is **not** about recovering after sleep/reboot/crash in the sense of resuming interrupted work — it's about **process-supervision self-healing**: making sure every currently-running claude session has exactly one live watcher, regardless of how coverage was lost. The systemd timer / launchd agent just runs this on a 5-minute cadence so the gap self-heals without a manual step (`OnStartupSec=2min`, then `OnUnitActiveSec=5min` per the systemd timer; equivalent `RunAtLoad` + `StartInterval=300` for launchd).

**This is a fundamentally different animal from anything in Limit Buster's architecture**, because Limit Buster has no equivalent of a "detached background watcher process per session" — it's a VS Code extension running inside one long-lived extension host, and per the brief it has `liveSessions.ts` (`claude agents --json`) as its live-panel check. Reconcile's *problem* (orphaned/duplicate watcher processes) is specific to their process-per-pane, no-supervisor architecture; it should not read as "a feature we're missing" so much as "a failure mode we don't have because we're structured differently." That said, the **failure modes it catalogs are worth cross-checking against our extension-host lifecycle** — see For Limit Buster.

**Concrete engineering substance worth extracting even though the surrounding architecture doesn't map 1:1:**

1. **Coverage keyed per-pane, not per-pid (reconcile.js:433-445, "Finding 3").** A stopped-but-not-exited claude keeps its monitor alive; keying coverage by pid would arm a *second* monitor for a new foreground claude in the same pane, and both would send keys — a literal double-send bug class. Fix: coverage is a set of panes, and a `running` entry only counts if its monitored pid still resolves to that pane in the CURRENT process tree (a dead pid's coverage doesn't count either — that monitor is about to self-exit anyway).
2. **pgrep-probe fail-closed, not fail-open (reconcile.js:351-369, "Finding 2", `runningFromPgrep`).** If the coverage probe itself can't be trusted (pgrep missing, wrong flag dialect on BSD/busybox, unparseable output), the function **throws** rather than returning "zero covered" — because reporting zero would arm a duplicate monitor on every single timer tick. Comment: "Refusing to reconcile — reporting 'zero monitors' here would arm duplicate monitors." This is a clean instance of a general principle: **when a liveness/coverage check is unverifiable, fail closed (do nothing) rather than fail open (assume worst-case and act) if acting is itself the dangerous branch.**
3. **Cross-platform process-identity heuristics (reconcile.js:204-307, "Finding 6/7/8"), extensively tested (test/reconcile.test.js has ~25 tests just for `planReconcile`/`sessionTargetsByPane` variants).** Three ways to recognize "this process is a claude session": `comm === 'claude'` (normal case, process.title set); a `node`-comm process whose *executed script* basename is `claude` or matches the claude-code cli entry pattern (covers `process.title` unset — a shebang/`node` launch case); their own launcher wrapping an agent that embeds claude as a subcommand token (e.g., a fictional `happier claude` wrapper). Explicitly excludes: print-mode (`-p`/`--print`) sessions (never armed — injecting into piped/scripted output would corrupt it), and careful handling of `-p` as a *flag-position* check (not a bare substring) so a prompt that merely contains the text `-p` isn't misdetected as print mode. macOS/BSD `ps comm=` truncates to 16 chars and is a full path, not a bare name, requiring an argv0-basename fallback (`isClaudeProc`, reconcile.js:210-223) — a portability trap that's easy to miss if only tested on Linux.
4. **Single-instance lock with PID-reuse-proof identity and crash-safe stale-lock stealing (reconcile.js:42-184, "Finding 4," the single largest and most carefully commented block in the file).** Problem: a manual `reconcile` run overlapping a timer-fired run must not both arm the same monitors. Naive PID-based locking is unsafe because **PIDs get reused by the kernel** — a stale lock file's recorded PID could later belong to an unrelated live process, making the check "is holder alive?" wrongly say yes forever, permanently wedging self-heal. Their fix: lock identity is `"<pid>\t<processStartToken>"`, where `processStartToken` reads `/proc/<pid>/stat` field 22 (start time) on Linux, or falls back to `ps -o lstart= -p <pid>` pinned to `LC_ALL=C` (documented reasoning: `lstart`'s date format is locale-dependent, and a checker running under a different locale than the writer — e.g. launchd's bare-C-locale timer vs. an interactive shell — would see a false mismatch and wrongly steal a live lock). A second "breaker" lock file serializes the *removal* of a stale main lock, so exactly one concurrent runner ever breaks+recreates it, avoiding a double-hold race. The file documents (line 170-173) a residual ~0.2%-under-contention race they found via a **cross-process stress test** (test/reconcile.test.js line 149, "grants mutual exclusion across real concurrent processes") — accepted as bounded rather than eliminated, and explicitly called out as such.
5. **Self-expiring exclusion list (reconcile.js:186-202, "Finding 5", `exclude-self` CLI command).** A user can durably exclude the *current* session from auto-monitoring (e.g. while intentionally pasting rate-limit text for testing) by appending the claude PID to `~/.claude-auto-retry/reconcile-exclude`. Keying by PID rather than pane-id is deliberate: PIDs are unique-while-alive and the entry is pruned automatically once that PID dies (`pruneExcludeEntries`, filters out any purely-numeric entry whose process is no longer alive) — so a stale exclusion can never silently mute an unrelated *future* session that happens to reuse the same tmux pane id. Pane-id-form entries are explicitly NOT pruned (staleness can't be detected for them) and are documented as the less-safe, hand-managed fallback form.
6. **launchd/systemd unit substance (not just boilerplate):**
   - Both units solve the **same specific problem**: `reconcile` deliberately spawns *detached* monitor processes and then exits (a oneshot/short-lived job), but each service manager's *default* process-group cleanup would kill those freshly-spawned children along with the parent job unless overridden. systemd: `KillMode=process` (default is `control-group`, which would SIGKILL everything in the cgroup, including the fresh monitors — explicit `# CRITICAL` comment). launchd: `AbandonProcessGroup=true` for the equivalent reason, explicitly commented as "mirrors KillMode=process."
   - launchd's plist explicitly sets `PATH` to `/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin` because launchd jobs do **not** inherit the login shell's PATH (only the system default), so a Homebrew-installed `tmux` would otherwise fail with `ENOENT` — covers both Apple Silicon (`/opt/homebrew`) and Intel (`/usr/local`) prefixes.
   - systemd timer explicitly does NOT set `Persistent=true` and documents why: that only matters for wall-clock (`OnCalendar=`) timers; these are monotonic (`OnStartupSec`/`OnUnitActiveSec`), which "pause across suspend and resume on wake, so there is nothing for Persistent to catch up." This is a subtle, easy-to-get-wrong distinction between monotonic and calendar systemd timers.
   - Both first-run promptly after load/login (launchd `RunAtLoad`, systemd `OnStartupSec=2min`) specifically to "let a just-logged-in tmux settle" before the first reconcile pass, then repeat every 5 minutes thereafter.

## status-file.js, events.js, logger.js, bin/cli.js, bin/tmux-status.sh — state, status, CLI

Sources: `claude-auto-retry/src/status-file.js` (126 lines), `src/events.js` (82 lines), `src/logger.js` (48 lines), `bin/cli.js` (503 lines), `bin/tmux-status.sh` (89 lines).

**Persisted state, file by file:**
- **`status-file.js`** — one small JSON snapshot per watched pane, written on every monitor poll tick (default every 5s), under `~/.claude-auto-retry/status/<socketKey>_<paneKey>.json`. Purpose stated in the file's own header comment: the monitor's state lives only in-memory inside a detached, unref'd process, so nothing external can see it — this file is the sole channel for a shell script to render status without talking to the process. Written atomically (tmp + `rename`, status-file.js:61-63) so a reader never sees a half-written file. Timestamps are stored in **epoch seconds, not ms** — explicit reason given (status-file.js:9-11): BSD/macOS `date` has no `%N` for sub-second precision, so seconds keeps the POSIX reader script portable without a date-parsing dependency. Includes a **best-effort GC sweep** (`sweepStaleStatus`, called on monitor startup and from `uninstall`) that deletes status files whose `updatedAt` is stale (default 300s) or that are orphaned `.tmp` files from a write that died mid-rename — so the status directory doesn't grow unbounded over a machine's lifetime, since tmux pane ids increment monotonically per server and are never reused (comment, status-file.js:83).
- **`events.js`** — the `StopFailure` marker channel described in DESIGN-NOTES §1. One JSON marker per pane under `~/.claude-auto-retry/events/`, written by the hook process (a claude child), read/consumed by the monitor. `RETRYABLE = Set(['overloaded', 'server_error'])` (events.js:30) is the actual enforced allowlist backing the "rate_limit excluded" design decision — confirmed here in code, not just in the README prose. Handles a **socket-key migration**: current markers are filed under `<socketKey>_<paneKey>.json`, but a `legacyFileFor` fallback (no socket prefix) is checked too, "so an upgrade doesn't silently drop events mid-flight" (events.js:45-46) — a specific, concrete backward-compatibility mechanism for a format change across versions.
- **`logger.js`** — genuinely simple: `appendFile` to `~/.claude-auto-retry/logs/YYYY-MM-DD.log`, one file per calendar day, three levels (INFO/WARN/ERROR), with an hourly-throttled cleanup pass (`CLEANUP_INTERVAL_MS = 3600_000`) that deletes any `.log` file whose mtime is older than `MAX_AGE_DAYS = 7`. No log level filtering, no size cap per file — only age-based rotation.

**CLI commands, mapped to their implementation (bin/cli.js:467-502, the `switch` dispatch):** `install`, `uninstall`, `install-hook [dir]`, `uninstall-hook [dir]`, the hidden `_stopfailure-hook` handler (invoked BY Claude Code, not by a user — bin/cli.js:207,226-237), `reconcile [--dry-run]`, `exclude-self`, `install-timer`, `uninstall-timer`, `status`, `logs`, `version`. Notable implementation details:
- `cmdStatus` (bin/cli.js:172-185) just tails the last 10 lines of today's log file — no live monitor introspection, no aggregation across panes; genuinely minimal.
- `cmdLogs` (bin/cli.js:187-203) shells out to the real `tail -f` binary via `spawn`, inheriting stdio — not a reimplementation.
- The `StopFailure` hook installer/uninstaller (bin/cli.js:239-267) is **idempotent by construction**: it filters any existing hook entry whose JSON contains the literal marker string `_stopfailure-hook` before appending the current one (line 246), so re-running `install-hook` never duplicates the entry. `uninstall-hook` (255-267) cleans up empty `hooks.StopFailure` arrays and an empty `hooks` object entirely, rather than leaving cruft — a good hygiene detail, though note it is a **separate command from `uninstall`**, confirmed by reading `cmdUninstall` directly (see Install/Uninstall section below).
- `install-timer` / `uninstall-timer` (bin/cli.js:308-406) render the systemd/launchd unit templates by substituting the resolved Node binary path and this CLI's own absolute path, then actually enable/load them (`systemctl --user enable --now` / `launchctl bootstrap`) — not just files-dropped-on-disk, an active install. Both explicitly warn in their console output that the unit **pins the current Node path**, and must be re-run after an `nvm` version switch — the same Node-version-lock limitation the README states for the shell wrapper itself (Known Limitation #2), now confirmed to also apply to the timer units.

**tmux-status.sh, mechanically:** pure POSIX `/bin/sh` (explicit rationale in its own header: dependency-light hosts like Alpine/busybox need to run this every few seconds from every attached client cheaply, matching the "zero dependencies" claim — no `jq`, no `node`). Parses the JSON snapshot with `grep -o` pattern extraction rather than a real parser (tmux-status.sh:30-31, `'"status":"[^"]*"'` style), which is fragile in principle but workable given the writer fully controls the JSON shape. Staleness threshold is **derived from the snapshot's own recorded `pollIntervalSeconds`** (`interval * 2`, floored at 10s) rather than a fixed constant — explicit rationale (script comment, lines 37-43): a healthy monitor configured with a longer poll interval shouldn't have its segment blink blank for a large fraction of every cycle. A `gaveUp: true` flag in the snapshot is checked FIRST and overrides the normal per-`status` rendering (lines 50-58) — documented reason: several give-up code paths in the monitor deliberately leave `status` at whatever value it had when they stopped acting (so the scraper/event logic doesn't re-detect its own stale error next tick), and without an explicit flag the status bar would keep showing a live "monitoring"/"waiting" icon for a monitor that will never act on this pane again.

**Comparison with our status bar / log / persisted state:**
- **Status surface.** Their status is an *external, cross-process, polling* channel (JSON-on-disk, read by a separate shell process every `status-interval` tmux seconds) because their monitor is a detached, unref'd, headless Node process with no other way to be observed. Our `src/statusBar.ts` (98 lines) is a `vscode.StatusBarItem` updated in-process, in the same extension host that holds all state — architecturally simpler because there is no process boundary to cross. `CountdownStatusBar.update()` (statusBar.ts:36-93) takes a `PendingJob | undefined` plus a `waiting` count and a `mode: 'always' | 'pending' | 'never'`; it shows a live countdown (`formatDuration`), a rich Markdown tooltip (resume time, jitter padding, reason, session id, folder, an explicit **folder-trust warning** when `job.folderTrusted === false` — statusBar.ts:77-85, a specific safety affordance claude-auto-retry has no equivalent of, since it never deals with the CLI's own trust-prompt gate), and a background-color nudge in the final 60s. Their five-state icon vocabulary (`🟢` monitoring / `⏳` waiting-on-reset / `🟠` overload-backoff / `🛡` safeguard-retry / `🔴` given-up, tmux-status.sh:56-88) is a **useful state taxonomy to borrow conceptually** even though our status bar already covers the "waiting" state with a live countdown — see For Limit Buster on the give-up/gaveUp idea specifically, since a quick skim of statusBar.ts shows no equivalent "gave up, no further automatic action" terminal state distinct from "idle."
- **Logging.** Their `logger.js` persists dated, rotating files to `~/.claude-auto-retry/logs/` — durable across process restarts, crashes, and reboots, inspectable after the fact with a plain text editor or `tail -f` via `claude-auto-retry logs`. Our `src/log.ts` (18 lines) is a thin formatter (`ISO-timestamp [name] LEVEL message`) that writes through an arbitrary `Sink`; `extension.ts:84-85` wires that sink to `channel.appendLine()` on a plain `vscode.window.createOutputChannel('Claude Limit Buster')` — **not** the newer `LogOutputChannel` API (`createOutputChannel(name, {log: true})`), and not an explicit file. Whether VS Code persists a plain output channel's contents to disk across window reloads was not verified by reading VS Code's own source in this pass — flagging as **not verified**, a concrete thing worth checking, since if it does not persist, a resume that fires while the user is away (the entire point of this extension) leaves no durable trace to diagnose after the fact, which is exactly the gap claude-auto-retry's file-based logger closes for itself.
- **Persisted job state.** Their `reconcile-exclude` file and status/events directories are the closest analog to "durable state," all keyed by tmux pane id or claude PID and explicitly designed to be **self-expiring** (dead PIDs pruned on read) to avoid stale entries silently misapplying to a future, unrelated session (reconcile.js, "Finding 5", cross-referenced above). Our persisted state (`extension.ts:117-151`) uses VS Code's own `context.globalState` key-value store — `READY_KEY` holds an array of `PendingJob` objects written through on every change (`persistReady()`, extension.ts:126-127) and restored at activation (`restoredReady`, extension.ts:151); separate keys track the first-run prompt choice and update-check state (`FIRST_RUN_PROMPT_KEY`, `LATEST_TAG_KEY`, `LAST_CHECKED_KEY`, `DISMISSED_VERSION_KEY`). This is a **materially safer persistence model** than theirs by construction: `globalState` is scoped to the extension by VS Code itself (no filesystem path a user or another process can accidentally collide with or leave orphaned), and there is no pane-id-reuse-style ambiguity to guard against because there is no external multiplexer whose ids get recycled — the entire self-expiring/exclude-list machinery in their reconcile.js exists to compensate for a hazard (tmux pane id reuse) that our architecture doesn't have.

## Install / uninstall footprint — how much it touches the user's system

Derived from `bin/cli.js` `cmdInstall`/`cmdUninstall`/`cmdInstallHook`/`cmdUninstallHook`/`cmdInstallTimer`/`cmdUninstallTimer` (read directly, not inferred from README prose) plus `injectWrapper`/`removeWrapper` (bin/cli.js:24-67).

**Install touches:**
1. **Shell rc files** — `~/.bashrc` and/or `~/.zshrc` (whichever exist or match `$SHELL`; if neither, defaults to creating `.bashrc`), via `injectWrapper` (bin/cli.js:24-49): reads the current file, finds a `# >>> claude-auto-retry >>>` / `# <<< claude-auto-retry <<<` marker pair if present (removes the old block first — idempotent re-install), appends the rendered `wrapper.sh` template (with `__LAUNCHER_PATH__` substituted) between fresh markers. Fish shell is explicitly **not** auto-installed into — the CLI prints manual instructions and exits (bin/cli.js:135-140).
2. **tmux itself**, system-wide, via the OS package manager (`apt-get`/`dnf`/`pacman`/`apk`/`brew`), if not already present and new enough (>= 2.1) — this is a **sudo-invoking system package install**, the most invasive single step (bin/cli.js:85-108, `installTmux`).
3. **`~/.claude-auto-retry/` state directory** — created lazily on first write by whichever module needs it (logs, status, events, the reconcile lock and exclude file) — not created by `install` itself, but a direct consequence of using the tool.
4. **`install-hook`** (opt-in, separate step) — read-modify-write of `<CLAUDE_CONFIG_DIR or ~/.claude>/settings.json`, adding a `hooks.StopFailure` array entry (bin/cli.js:239-253). This is a **write into Claude Code's own configuration file**, not just claude-auto-retry's own state — the most consequential single touch-point on the user's system, since it changes Claude Code's own hook behavior for every session using that config dir, not just wrapper-launched ones.
5. **`install-timer`** (opt-in, separate step) — writes systemd `--user` unit files into `~/.config/systemd/user/` (or `$XDG_CONFIG_HOME/systemd/user/`) and actively enables+starts them via `systemctl --user enable --now` (bin/cli.js:358-393), or on macOS writes a LaunchAgent plist into `~/Library/LaunchAgents/` and loads it via `launchctl bootstrap` (bin/cli.js:311-346). This is a **persistent background service** that will keep running (and spawning monitor processes) independent of any single shell session, until explicitly uninstalled — the most durable/system-level footprint of the whole tool.

**Uninstall touches — confirmed by reading `cmdUninstall` directly (bin/cli.js:161-170), not inferred from the README:**
```js
async function cmdUninstall() {
  const bashrc = join(homedir(), '.bashrc');
  const zshrc = join(homedir(), '.zshrc');
  for (const rc of [bashrc, zshrc]) { await removeWrapper(rc); }
  await sweepStaleStatus().catch(() => {});
  console.log('Shell function removed. Restart your shell to complete.');
}
```
So plain `uninstall` **only**: strips the marker-delimited block from `.bashrc`/`.zshrc`, and best-effort GCs stale status files. It does **not**: remove the `StopFailure` hook from Claude Code's `settings.json` (requires the separate `uninstall-hook` command — confirmed, this is not a guess), does not stop or remove the systemd/launchd timer (requires the separate `uninstall-timer` command), does not remove `~/.claude-auto-retry/` itself (logs, events dir, reconcile-exclude file, reconcile lock all survive), does not `npm uninstall` the package (a manual second step per the README), and — most notably — **does not kill any currently-running detached monitor processes**; `uninstall-timer`'s own success message says so explicitly ("Already-running monitors are unaffected," bin/cli.js:352,405), and plain `uninstall` doesn't even mention them. So a user who ran `install-hook` and/or `install-timer` and then runs only `uninstall` is left with: a live `StopFailure` hook still firing into every Claude Code session using that config dir, a live systemd/launchd timer still re-arming monitors every 5 minutes, and any monitors already running continuing to watch their panes and inject "continue" — all silently, since `uninstall`'s own console output ("Shell function removed... complete") gives no indication that anything else is still active. This is **not a claim in the README being contradicted** — the README's own CLI Commands table and "Uninstall" section do list `uninstall-hook` and `uninstall-timer` as separate commands and does say plain uninstall's scope is "removes the shell function... tmux is left installed" — but a user relying on memory of "just run uninstall" (the README's own top-level Uninstall section only shows `claude-auto-retry uninstall` + `npm uninstall -g`, not the hook/timer commands) would reasonably not expect this. Confirmed by code, not by README ambiguity alone.

**tmux itself is explicitly left installed** on uninstall (README's own stated scope, corroborated by `cmdUninstall` containing no tmux-removal logic at all) — reasonable, since tmux is a general-purpose tool the user may have wanted independently, but worth noting as one more thing that outlives the tool.

## For Limit Buster

Ranked adopt / consider / avoid. Each cites the evidence (file:line in claude-auto-retry) and the file in our repo it would touch.

### Adopt

1. **A `~/.claude/settings.json` note anchored to `error_type`, not just error text — check whether our trust gate already gets this.** claude-auto-retry's biggest single architectural regret, stated in its own words, is that its base detection scrapes "a human-facing render" (DESIGN-NOTES.md:9-17) and every false positive/negative traces to that choice. Their fix was Claude Code's `StopFailure` hook, verified against the decompiled v2.1.195 binary to carry a typed `error` field with 9 values (DESIGN-NOTES.md:92-104, events.js:30 `RETRYABLE = Set(['overloaded','server_error'])`). The brief states Limit Buster already has a trust gate that "believes limit text only when it appears in a genuine API-error entry" — i.e., we may already be ahead of their base scraper by reading structured JSONL rather than a rendered pane. Action: not new code, but worth a deliberate check (by whoever owns `trust.ts`/`parsers/*`) that our JSONL entries expose the same typed `error`/`isApiErrorMessage` fields claude-auto-retry independently discovered (DESIGN-NOTES.md §2, `isApiErrorMessage: true` on the last `type:"assistant"` record) — if so, this is confirmation our approach is structurally the "supersedes the scraper" endpoint they were reaching for; if we're still substring-matching rendered text anywhere, that's the gap to close. Touches: `src/parsers/limitParser.ts`, `src/parsers/overloadParser.ts`, `src/trust.ts`.

2. **The near-limit wrap-up nudge is a specific, verbatim, checkable string we may be structurally blind to.** At ~95% of the 5-hour window, Claude Code prints `⏺ Approaching your 5-hour usage limit — Claude will wrap up the current step.` (README.md:454, config.js:102-115) — not an error, no limit banner, the turn ends cleanly with the prompt idle, and nothing resumes it; a session can sit parked for hours past the real reset. claude-auto-retry's own comment calls this "a server-side Claude Code behavior with no user-facing switch (feature-flagged, not a setting)" (README.md:459-461) — i.e., they had to reverse-engineer it because there's no structured signal, only this exact rendered notice. Since our trust gate is keyed on genuine API-error entries, this notice (not an error) may fall entirely outside what we watch for. Action: check `limitParser.ts` (or wherever transcript records are classified) for whether a non-error assistant message containing this exact string is ever surfaced as a resumable event; if not, decide deliberately whether to add it rather than silently inherit the gap. Touches: `src/parsers/limitParser.ts`, `src/extension.ts` (whatever schedules resumes off parsed events).

3. **A flat fallback wait for an unparseable reset time.** Their `fallbackWaitHours` (default 5, config.js `DEFAULT_CONFIG.fallbackWaitHours`) is what they wait when the limit banner's reset time can't be parsed at all — distinct from their `maxWaitHours`-style sanity ceiling. Our `config.ts` has `maxWaitHours` (default 24, described as "ignore a reset time further out than this, which is usually a misparse") but nothing found in `config.ts` for "what do we do if parsing the reset time fails entirely" — that looks like a real behavioral gap, not just a naming difference: their tool has an explicit, bounded action (wait a flat window and retry) for total parse failure, and ours may currently do nothing (silently drop the event) or something unverified in this slice's file scope. Touches: `src/config.ts`, `src/scheduler.ts` (out of this slice's assigned files — flagging for the scheduler-slice owner to confirm current behavior on unparseable reset times).

4. **Log durability across restarts.** claude-auto-retry writes dated, 7-day-rotated log files to `~/.claude-auto-retry/logs/` (logger.js) specifically so a resume that happens while the user is away leaves an inspectable trail. Our `src/log.ts` pipes through a plain `vscode.window.createOutputChannel` (extension.ts:84-85), not the `LogOutputChannel` API and not an explicit file — whether that content survives a VS Code window reload was **not verified** in this pass (flagged, not asserted). Given the extension's entire purpose is unattended overnight operation, an unattended failure with no durable log would be a real usability gap if the output channel doesn't persist. Action: verify (quick, not part of this slice) whether `createOutputChannel` content survives a reload; if not, either switch to `{log: true}` (which VS Code does persist to the extension host's own log directory) or add explicit file logging analogous to logger.js. Touches: `src/log.ts`, `src/extension.ts`.

5. **A terminal "gave up" state, distinct from idle.** tmux-status.sh:50-58 checks an explicit `gaveUp: true` flag before anything else, specifically because several of the monitor's own give-up code paths leave the underlying `status` field at whatever it was mid-flight — without the explicit flag, "given up, will never act again on this" is indistinguishable from "healthy and still watching." Worth checking whether our `statusBar.ts`/`scheduler.ts` model has an equivalent explicit terminal state (e.g. "budget refused and job dropped," "max wait exceeded, abandoned") distinct from plain idle/no-job — a skim of `statusBar.ts` shows only `job present` vs `no job` (falls back to the idle "$(eye)" view per statusBar.ts:41-54), with no visibly distinct "we tried and gave up" affordance. Touches: `src/statusBar.ts`, `src/scheduler.ts`.

### Consider

6. **Full jitter, not just proportional, for the overload/backoff path.** DESIGN-NOTES §3 recommends `random(0, base)` full jitter specifically for 529 (global capacity, not per-key) so a fleet of independent clients doesn't resynchronize into the same overload window — explicitly framed as low single-client impact, real ecosystem impact. Notably this is a **proposal in their own doc, not shipped** (their default `jitterMode` stays `proportional`). Worth considering for our overload-path randomization (if `overloadParser.ts`/`scheduler.ts` schedules overload retries on a fixed or proportional-jitter backoff) since we'd be adopting an idea they identified but didn't act on — cite it as "their own unshipped proposal," not as their established practice. Touches: `src/randomDelay.ts`, `src/scheduler.ts`.

7. **Self-expiring exclusion, if we ever need a "don't touch this session" escape hatch.** `exclude-self` (reconcile.js:551-562) durably excludes the *current* session by its process id, and the exclusion **automatically expires** when that process exits (`pruneExcludeEntries`, reconcile.js:189-191) — explicitly chosen over a pane-id form because a stale pane-id exclusion could silently mute an unrelated future session (tmux reuses pane ids; our architecture has no pane-id-reuse hazard at all, but the general pattern — "prefer identity keys that can't outlive their referent" — is worth keeping in mind if we ever add a per-session opt-out). Given our issue #6 already tracks not forking a session a VS Code panel still holds open (per the brief's `liveSessions.ts`), a manual "don't touch this one" override might be a natural complement if not already covered. Touches: `src/liveSessions.ts` (to check if this is already implicitly covered), `src/extension.ts`.

8. **Fail-closed on unverifiable liveness checks.** `runningFromPgrep` (reconcile.js:351-369, "Finding 2") throws rather than reporting "zero covered" when the coverage probe itself can't be trusted — because reporting zero would be the *dangerous* branch (arms duplicate monitors). This is a general principle, not tool-specific: wherever `liveSessions.ts`'s `claude agents --json` call could fail or return ambiguous output, the safe default should be "assume live / don't act" rather than "assume gone / go ahead and fork," mirroring their reasoning. Worth a targeted check of `liveSessions.ts`'s own failure-handling, out of this slice's file assignment but flagged for whoever owns it.

### Avoid / already ahead — don't inherit these

9. **We do not need reconcile, the launchd/systemd timer, pane-id-reuse handling, or the single-instance lock at all — and should not add analogs.** All four exist to solve problems specific to claude-auto-retry's architecture: a detached, unsupervised, per-pane Node process with no host-level lifecycle hook, driving a terminal multiplexer whose pane ids get recycled by the OS/tmux itself. Limit Buster runs inside one long-lived VS Code extension host, with state in `context.globalState` (a VS Code-managed, collision-proof store — extension.ts:117-151) rather than files on disk keyed by an externally-recyclable id. Adding a "reconcile" analog would be solving a problem we don't have. This is explicitly a case where **we are ahead by construction**, not by more code.

10. **No shell rc injection, no sudo package installs, no persistent background OS service.** claude-auto-retry's install touches `.bashrc`/`.zshrc` (bin/cli.js:142-158), can invoke `sudo apt-get`/`dnf`/`pacman`/`apk` to install tmux system-wide (bin/cli.js:85-108), and its opt-in `install-timer` actively loads a systemd `--user` timer or launchd LaunchAgent that persists and keeps running independent of any single shell session (bin/cli.js:311-346, 358-393) — confirmed by reading `cmdInstall`/`cmdInstallTimer` directly. A VS Code extension's install/uninstall lifecycle (activate/deactivate via the Extensions view, or VSIX install/uninstall) touches none of the user's shell configuration, requires no sudo, and leaves no independent background service running once uninstalled — this is a structurally safer install footprint, not an incidental one. Nothing to adopt here; worth stating explicitly in our own docs as a stated advantage if we ever compare footprints publicly.

11. **`uninstall` leaving the `StopFailure` hook and the reconcile timer live is a trap worth naming, not copying.** Confirmed by reading `cmdUninstall` (bin/cli.js:161-170) directly: plain `uninstall` strips only the shell wrapper and sweeps stale status files — it does not touch `settings.json`'s `hooks.StopFailure` entry (needs `uninstall-hook`) or the systemd/launchd timer (needs `uninstall-timer`), and does not kill already-running monitors (`uninstall-timer`'s own success message says so explicitly: "Already-running monitors are unaffected," bin/cli.js:352,405). If Limit Buster ever grows a similarly layered install (e.g. an opt-in background watcher outside the extension host, or a write into Claude Code's own `settings.json` for a hook), the lesson is: a single "uninstall" entry point should either remove everything it's capable of installing, or the top-level docs must not present a bare `uninstall` as sufficient. Not applicable to current Limit Buster (no such layering exists per the brief's file list), but worth keeping in mind if `docs/NEXT.md` ever proposes a Claude Code hook integration.

12. **The budget guard has no analog in claude-auto-retry at all — confirmed absence, not just unmentioned.** Skimmed `config.js`, `README.md`, and `DESIGN-NOTES.md` in full: there is no cost/token estimation, no refusal-to-resume-if-expensive path, nothing resembling `maxResumeTokens`/`budget.ts`. Their tool will retry-inject "continue" an unbounded number of times (up to `maxRetries`) with no awareness of what a cold resume costs to rebuild context for. This is a clear area where Limit Buster is ahead, not a gap to close.
