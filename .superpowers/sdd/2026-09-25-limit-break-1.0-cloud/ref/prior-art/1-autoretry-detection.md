## Our repo's detection/trust architecture (read for comparison — code)

- `src/parsers/limitParser.ts`: `looksLikeLimitMessage()` gate (LIMIT_HINTS, line 49-63) then an ordered `RULES` array (line 129-199) tried in order — epoch timestamp, ISO timestamp, duration-hours, duration-minutes, clock-reset, clock-retry — first rule producing a future Date within `maxWaitHours` (default 24h) wins. `looksLikeCode()` (line 363-365) is the false-positive guard: rejects text containing `{};`, `=>`, JS keywords, `//`, `/*`, or backtick — applied only when `!opts.trusted`.
- `src/parsers/overloadParser.ts`: separate `looksLikeOverloadMessage()` gate that explicitly excludes anything `looksLikeLimitMessage()` already claims (line 51-53, "A 429 is a rate limit, not an overload... belongs to the limit parser"), then `ERROR_MARKERS` (error/failed/unavailable/overloaded_error/leading "Overloaded"/timed out/socket hang up/5xx) gates a `RULES` array matched by regex (api-error-status, overloaded, server-error, connection-error, timeout). Code-guard is `quotesSourceCode()` for `API Error` lines (narrower, since real errors embed JSON) vs the shared `looksLikeCode()` otherwise.
- **Trust gate is NOT in `src/trust.ts`.** `src/trust.ts` is the Claude Code *folder*-trust-dialog check (`hasTrustDialogAccepted` in `~/.claude.json`) — unrelated to limit-message trust, confirmed by reading the whole file (95 lines): it answers "will `claude --resume` hit a trust prompt in this cwd," not "is this limit text real." The actual message-trust gate the brief describes lives in `src/transcriptWatcher.ts`: `isRateLimitEntry()` (line 469-477) and `isApiErrorEntry()` (line 484-493) check **structural JSONL fields** — `entry.isApiErrorMessage === true`, `entry.apiErrorStatus`/`entry.status` in the 5xx or 429 range, `entry.error` being a non-empty string. `collectStrings()` (line 500-520) then recursively pulls every string >8 chars out of the whole entry object (tool inputs, tool results, error fields, message content — anything, to depth 6, capped at 200 strings) as `candidate`s, and each candidate is passed to `detectLimit(candidate, now, maxWait, { trusted: flagged })` (line 419) — so `trusted` is **entry-level**, not candidate-level: if the entry as a whole carries a genuine API-error/rate-limit marker, *every* string pulled out of it (including a tool's own quoted arguments) skips the `looksLikeCode` guard.
- This is fundamentally the same design principle claude-auto-retry converges on through much more machinery (tool-echo masking, prompt-glyph vetoes, `API Error`-line anchors): don't trust prose in isolation, trust it because of where it structurally sits. Ours gets this almost for free from the JSONL transcript's own schema; theirs has to reconstruct it heuristically from a scraped terminal pane because that's all a tmux pane gives them. **This confirms and extends `docs/PRIOR-ART.md`'s existing finding** ("Detection by structured field beats detection by prose... Claude-Autopilot... Issue #25... PR #26... 'support various bullet characters'") — that finding was made against a different prior-art repo (Claude-Autopilot) but claude-auto-retry is an even richer example of the same lesson, at far greater implementation cost than ours pays.

## Three gaps found by direct execution against our own compiled parser (read-only)

All three verified by running `out/src/parsers/*.js` directly (no source modified, no `npm run compile` run — `out/` was already present from a prior build):

**1. Tool-echo / quoted-text false positive on untrusted candidates (equivalent of their issue #63).**
Our `collectStrings()` walks the *entire* JSONL entry recursively, so a tool call that merely **quotes** limit-shaped text — e.g. a `Bash` tool's own `grep` argument, or a `Read`/`Grep` tool's result content — becomes a `candidate` string tested with `trusted: false` (since the entry itself isn't a genuine API-error entry). The only defense for an untrusted candidate is `looksLikeCode()`, which does **not** reject plain quoted prose. Verified directly against `out/src/parsers/limitParser.js`:
```
detectLimit('grep -c "5-hour limit reached - resets 3pm (UTC)" ~/logs/2026-07-18.log', now, 24, {trusted:false})
  => DETECTED, resumeAt = 2026-09-24T15:00:00.000Z
detectLimit('[16:29:37] 5-hour limit reached - resets 3pm (UTC)', now, 24, {trusted:false})
  => DETECTED, resumeAt = 2026-09-24T15:00:00.000Z
```
Both are exactly the shape of claude-auto-retry's dated, real incident (patterns.test.js:18-21, "before the fix it parked the monitor for the parsed hours (a real 22.5h incident)" and tool-echo.test.js:23-31 reproduces the report almost verbatim: `grep -c "5-hour limit reached - resets 3pm (UTC)" ~/.claude-auto-retry/logs/2026-07-18.log`). No test in `test/transcriptWatcher.test.ts` or `test/parsers/limitParser.test.ts` covers a tool-use/tool-result string containing quoted limit text (confirmed by `grep -n "grep\|tool_result\|tool_use\|echo\|quoted" test/transcriptWatcher.test.ts` → no matches).

**2. Overload parser does not distinguish Claude Code's own in-flight retry from a terminal failure (their `WORKING_PATTERNS`/`isInternalRetry` distinction, patterns.js:804-814, overload.test.js:83-85).**
Verified against `out/src/parsers/overloadParser.js`:
```
detectOverload('API Error (529 {"type":"error"}) · Retrying in 5s · attempt 3/10')
  => DETECTED status=529 rule=api-error-status   (same result as the terminal colon form)
detectOverload('API Error: 529 Overloaded')
  => DETECTED status=529 rule=api-error-status
```
Both the parenthesised "Claude Code is still retrying" form and the terminal colon form are detected identically. `src/policy.ts:38-43` (`planResume`) schedules an actual resume off any `overload` detection ("An overload has no stated reset time, so the jitter *is* the backoff" — `resumeAt` defaults to `now` + jitter). If a transcript entry can carry the in-flight-retry rendering (not confirmed either way in this slice — DETECTION only, no read of how/when transcriptWatcher polls mid-turn), this would schedule a real `claude --resume ... "Continue..."` while Claude's own backoff is still in flight. Flagged as a **verified parser-level gap**, with the production-impact question (does a mid-retry transcript entry actually exist and get read before the turn settles) left open — that's an execution/timing question outside this slice's file list.

**3. "temporarily limiting requests (not your usage limit)" 429-style render is silently dropped by BOTH parsers.**
Claude Code's dedicated wording for a transient 429 — `"API Error: Server is temporarily limiting requests (not your usage limit) · Rate limited"` (claude-auto-retry's own fixture, overload.test.js:39, 65-67; their `OVERLOAD_ANCHOR`/pattern set explicitly recognises it as overload, NOT a usage limit, per their comment "A 429 is a rate limit, not an overload" mirrored almost word-for-word in `overloadParser.ts:48-53`) — is silently dropped by our repo entirely:
```
overloadParser.detectOverload('API Error: Server is temporarily limiting requests (not your usage limit) · Rate limited')
  => not detected   (looksLikeOverloadMessage rejects it: looksLikeLimitMessage() is true first, due to "Rate limited"
                      matching /\brate[- ]limit(?:ed|s)?\b/i in LIMIT_HINTS, so looksLikeOverloadMessage's own
                      explicit "a 429 belongs to the limit parser" carve-out routes it away from overload)
limitParser.detectLimit('API Error: Server is temporarily limiting requests (not your usage limit) · Rate limited', now, 24, {trusted:true})
  => undefined   (looksLikeLimitMessage is true, but no RULE finds a reset time — the message carries none —
                  so detectLimit returns undefined and the notice is discarded with no action taken at all)
```
This is a genuine three-way miss: not treated as overload (which is what claude-auto-retry treats it as, and which is the CORRECT read per the message's own text — it explicitly says "not your usage limit"), not treated as a limit with a resolved time, and not given any fallback wait either. The word "Rate limited" in Claude Code's own render is what defeats our `looksLikeLimitMessage`-based disambiguation between the two parsers. Both `LIMIT_HINTS` (limitParser.ts:54, `/\brate[- ]limit(?:ed|s)?\b/i`) and the overload/limit carve-out (`overloadParser.ts:51-53`) would need to special-case this exact phrase, or (their approach) require a *nearby* reset-time-shaped clause before letting "rate limit" vocabulary claim a message as a limit rather than an overload.



## test/tool-echo.test.js, safeguard.test.js, overload.test.js, stream-interrupted.test.js (read in full — tests)

These four files are the empirical false-positive-guard suite the brief asks about. Consolidated findings (each claim is test-derived):

### Tool-echo guard (tool-echo.test.js, all cases)
- Core mechanism already described from patterns.js: banner/error/safeguard text quoted as a `grep` **argument** inside a `● Bash(grep "5-hour limit reached..." ...)` header, or in the **result** lines under `⎿`, must never fire `isRateLimited`/`detectOverload`/`safeguardMatch`. Verified for all three families with near-identical fixtures (tool-echo.test.js:22-118).
- Control cases prove the guard is precise, not a blanket suppressor: the SAME text unquoted at the prompt fires (line 44-51); a real banner sitting ABOVE a small tool-call render still fires (line 53-61); a fresh quoted grep line does not steal `findRateLimitMessage`'s bottom-up scan away from a real banner beneath it (line 63-72); a live banner rendered as a `└` child of a NON-`Name(` notice ("● Agent \"...\" finished") still fires — the mask is keyed to `● Name(` headers specifically, not any `●`/`⎿` glyph combination (line 74-84); a bare `● API Error:` line (glyph without the `Name(` call-shape) is not mistaken for tool echo (line 86-93).
- **Print mode exemption confirmed by test** (line 95-100): with `tailLines=0` (used for piped/spawned process output, not the live TUI), the SAME quoted/JSON error shape that would be masked in TUI mode DOES fire — comment: "quoted errors are the REAL signal" in that mode. This is an important design point: the tool-echo mask is TUI-scan-only, deliberately not applied to piped output.

### Safeguard guard (safeguard.test.js)
- Verbatim real render fixture (worth keeping as data, quoting exactly): `"● API Error: Fable 5's safeguards flagged this message (https://www.anthropic.com/legal/aup). They may flag safe, normal content as well. Claude Code can't respond to this request with Fable 5."` followed by `"Double press esc to edit your last message, or try a different model with /model."` — note this is Claude Code's real AUP/safeguard-trip message, not a rate limit.
- Same anchor discipline as overload: fires only with an `API Error` line nearby (default pattern list includes `'safeguards flagged this message'`); explicitly tested to NOT fire on Claude answering a question that mentions the AUP link or explains "safeguards flagged this message" without an API Error line present (line 50-55, 195-207) — this is presented as a "regression" (i.e. a real historical bug) for unanchored patterns.
- Not fired on the phrase merely sitting far up in scrollback (tail-anchored) even with the API Error line present, if it's outside the tail window (line 61-64).
- **Bounded retry** via `maxRetries` (default 3, confirmed by `DEFAULT_CONFIG.safeguard.maxRetries === 3`, line 81-85) — after exhausting retries the monitor "gives up loudly ONCE, then holds quietly" (`safeguard-gave-up` then `safeguard-holding`, no further sends, line 184-193) rather than looping forever. A per-pane state machine (`s.status`, `s.safeguardAttempts`) governs this, tracked in `monitor.js` (not in our detection slice, only referenced).
- **Attempt-counter integrity under interleaved "working" ticks** (line 148-182): a documented regression where a tick landing while the retried request was in flight used to reset the attempt counter to 0 via the "clear" path — so a *sticky* AUP flag re-entered with a fresh retry budget every cycle and the max-retries cap never tripped (observed: "10+ sends with maxRetries=3"). Fixed by deferring (not clearing/resetting) while Claude is working. This is a subtle statefulness bug class specific to a polling architecture, worth flagging generically even though our architecture (event-driven off JSONL entries) differs.
- Family precedence: a co-present usage-limit banner takes precedence over a safeguard flag (line 217-222) — the state machine checks usage limit first.
- Disabled-by-config short-circuits entirely (line 230-235) — safeguard detection is opt-out, not hardcoded-on.

### Overload guard (overload.test.js) — richest false-positive fixture set of the four
- **Explicit historical false-positive regression set** (line 47-53, labeled in comments as "the exact false positives that injected 'Continue where you left off.' into live sessions" — i.e. real incidents, not hypotheticals): a bare status number in conversation (`"got a 529 back"`), Express code under edit (`res.status(503)`), a Dockerfile HEALTHCHECK comment mentioning "500"/"503", a `status.claude.com` mention in prose, and a bare `"500 Internal server error"` with no `API Error:` frame — none of these fire. The anchor requirement (`API Error` line, same discipline as safeguard) is what stops each of these.
- Recognised overload/5xx renders, confirmed patterns (`DEFAULT_OVERLOAD.patterns`, referenced not fully enumerated in this file, but individual matches tested): `API Error: 529`, `API Error: 500 Internal server error`, `API Error: 503 no healthy upstream`, `API Error: 502 Bad Gateway`, `API Error: 504 Gateway Timeout`, the `overloaded_error` JSON type embedded after an `API Error:` line, and a **dedicated 429-style render with no 3-digit code**: `"API Error: Server is temporarily limiting requests (not your usage limit) · Rate limited"` (line 33-40) — note the render text itself explicitly disclaims being a usage limit, and the pattern set explicitly distinguishes it from one.
- **Terminal vs. transient distinction is load-bearing** (line 83-85): the render `"API Error (529 {...}) · Retrying in 5s · attempt 3/10"` (parens form, Claude Code's own internal retry) must NOT fire — "Acting on it would interrupt Claude's own backoff." Only the **colon** form (`API Error: 529`) with no retry suffix is treated as terminal/actionable. This exact distinction (parens=retrying vs colon=terminal) is a specific, reusable heuristic.
- Depth-bounding: an error more than the tail window (12 content lines) up doesn't fire (line 89-92); AND a separate raw-distance cap (`OVERLOAD_MAX_RAW_LINES=20`) stops an error from being reached by chrome-stripping past a tall widget even when nothing but chrome intervenes (line 98-116, "Finding 6").
- **Backoff schedule tested precisely**: `[30, 60, 120, 240, 300]` seconds then steady-state 300s, with configurable `jitterPct` (default 15%, clamped 0-100) applied via `applyJitter` (symmetric, tested at rand-extremes 0/1/0.5). `maxTotalWaitMinutes` (default 120) caps the total overload wait before giving up (`overload-gave-up`).
- **Event-path vs scraper-path duality**: this tool ALSO listens for an out-of-band "StopFailure" event/marker (apparently a Claude Code hook, not something in our JSONL-transcript model) as an *authoritative* trigger, separate from the always-on pane-scraping detector. Extensive tests ensure the two don't double-fire on the same banner, that a non-retryable marker (`rate_limit`, `billing_error`, `invalid_request` — explicitly named as possibly from "an outdated hook") is consumed-and-ignored rather than acted on, and that backoff state resets cleanly across independent incidents without leaking escalation across days-apart outages. This whole event-marker mechanism is OUT OF SCOPE for our slice (it's about a companion hook, not text detection) but worth a one-line mention since it demonstrates a second, non-text detection channel this tool uses that we don't have.
- Family precedence: usage-limit still takes precedence over overload when both co-present (line 295-300, 473-480).

### Stream-interrupted guard (stream-interrupted.test.js)
- Real verbatim fixture (captured from an actual incident per the code comment, "tmux pane %111"): `"⏺ API Error: Your computer went to sleep mid-response. The response above may be\n  incomplete."` followed by a `✻ Cooked for 13m 58s` idle spinner and an empty prompt — the turn ENDS at idle, nothing resumes until something is typed (this tool then types a resume message).
- Sibling render family recognised (same finalizer, different causes) — verbatim: `"API Error: The response stopped arriving. The response above may be incomplete."`, `"API Error: Connection lost mid-response. The response above may be incomplete."`, `"API Error: Server error mid-response. The response above may be incomplete."`, `"API Error: The response stalled before a response was produced. Try again."`, `"API Error: Connection lost before a response was produced. Try again."` — i.e. suspend/sleep, dropped connection, stalled stream, and generic server error mid-response are ALL treated as the same recoverable class, distinct from both usage-limits and 5xx-overload.
- **Shape discriminator confirmed precisely by test, not just comment**: a render's head must BEGIN its line, optionally behind a message glyph (`⏺`/`●`) — an INDENTED, glyph-less `API Error:` line is treated as a hanging-indent quotation and does NOT fire (line 100-107, 109-115), even though the exact same phrase with the glyph at column 0 DOES fire. A disclosed/accepted false positive remains: a quotation that reproduces the glyph flush-left is indistinguishable from a real render and DOES fire (line 133-143, "KNOWN BOUNDARY") — but the cost is called low because the action taken (a single bounded "continue" that self-clears) isn't a multi-hour wait.
- Does not fire on: the phrase typed by the user behind the prompt glyph (line 79-81); the render with no `API Error:` head at all (ordinary prose using the same words, line 83-84); the render quoted inside a tool's grep result (line 86-94); the render sitting outside the tail window / far up in scrollback (line 145-149); model prose explaining the feature that quotes the phrase mid-sentence (line 72-77, 269-279).
- Does NOT walk its 2-line wrap window across a block boundary into an unrelated adjacent render's continuation (line 125-131) — i.e. the wrap-following logic stops at the first flush-left line even if that line is itself part of a different (non-matching) block.
- **Bounded retries** (same shape as safeguard): `DEFAULT_CONFIG.streamInterrupted.maxRetries <= 3` (line 172-176), gives up after exhausting attempts, and — same subtle bug class as safeguard — a documented fix ensures a "working" tick during the retry window defers rather than resets the attempt counter (implied by symmetry with safeguard.test.js; stream-interrupted.test.js's own version is at line 239-246, "WITHOUT resetting the attempt counter").
- Family precedence: usage-limit still wins over a co-present truncation render (line 262-267).

### Cross-cutting takeaway from all four guard files
Every non-limit false-positive family (overload, safeguard, stream-interrupted) uses the exact same anchor discipline: require a literal `API Error` (or, for stream-interrupted, the render's own head literally starting with `API Error:`) within a small nearby window, rather than trusting a bare phrase-match anywhere in the pane. This is presented consistently as the fix for a **named historical incident class** ("the tool's own diagnostic text matched /temporarily limiting requests/", "injected 'Continue where you left off.' into live sessions", "a genuinely limited idle session ... would never be retried"), not a theoretical concern — i.e. every guard exists because it broke in production first.

- **Calendar-dated reset tests** (lines 197-234): `"resets Aug 21 at 3pm (Australia/Brisbane)"` parses month=7 (0-based, Aug), day=21; long-form `"resets August 21, 3:30pm (UTC)"` also parses (comma-separated variant); clock-only forms carry `month: undefined, day: undefined`; wait is computed as literal days-until (e.g. exactly `(3*24+5)*3600_000` ms for a date 3 days out); a dated reset already in the past means "retry now" (only margin, no forward roll — since the org's next limit already reset); year inference across a Dec→Jan boundary is tested explicitly (`month: 0, day: 2` seen on Dec 30 → resolves to next year's Jan 2).
- **time-parser-tz.test.js is a dedicated host-timezone-independence suite**: it spawns a **child process** with `TZ` env var set to different host timezones (`Pacific/Auckland`, `UTC`, `America/New_York`, `Asia/Tokyo`) to prove `calculateWaitMs` gives the *same* wait regardless of what timezone the *host machine* itself is running in — Node fixes `TZ` at process startup, so this can't be tested in-process. Explicit rationale: this is a regression suite for "issue #60" (host==banner tz case) and a follow-on "date-anchored correction" for the general case (banner tz beyond UTC±12, or host/banner offset split >12h), which used to land the convergence loop on the wrong calendar day and overwait by ~24h.
- DST correctness is tested for **both** US (`America/New_York`) and EU (`Europe/Zurich`) fall-back nights, plus US spring-forward, plus explicit **rolling onto a transition day**: a nonexistent wall-clock time (spring-forward gap, e.g. "2am" during the skip) resolves to the first real instant at/after it, tested across 3 different host timezones to confirm it's host-independent; an ambiguous/repeated wall-clock time (fall-back repeat, e.g. "2am" occurring twice) resolves to the LATER occurrence, also tested across 3 hosts. A UTC+14 banner (`Pacific/Kiritimati`) is tested too, beyond the more common UTC±12 boundary case.
- No test coverage found for weekday-name parsing ("Monday", "next Tuesday") actually resolving to a Date — the only weekday-bearing fixture in the whole prior-art repo is `patterns.test.js`'s `'weekly limit resets 9am Monday'`, and that test only asserts `findRateLimitMessage` returns the raw string (render detection), not that `parseResetTime`/`calculateWaitMs` produces a correct Date from it. Labeled a GAP, not a confirmed capability — will verify against `parseResetTime` directly if time permits, but not proven present in code (RESET_TIME_REGEX has no day-name alternation) or tests.


## src/time-parser.js (read in full — code)

Two top-level parse shapes from `parseResetTime(text)` (time-parser.js:8-48):
1. **Absolute** via `RESET_TIME_REGEX` (line 5): `/resets?\s+(?:on\s+)?(?:([a-z]{3})[a-z]*\.?\s+(\d{1,2})(?:st|nd|rd|th)?,?\s+)?(?:at\s+)?(\d{1,2})(?::(\d{2}))?\s*(am|pm)?\s*(?:\(([^)]+)\))?/i`. Captures: optional month (matched by first-3-letters so "Aug"/"August" both work), optional day-of-month with ordinal suffix, hour, optional minute, optional am/pm, optional parenthesised timezone string (raw — validated later via `Intl.DateTimeFormat`, not a fixed list). A month token that ISN'T a real month name (e.g. "resets tomorrow 3pm") makes the whole match return `null` (line 14-15) rather than silently misreading "tomorrow" as a day — no "tomorrow"/"today"/weekday-name support was found in this regex or file.
2. **Relative** via `RELATIVE_TIME_REGEX` (line 6): `/(?:try again|wait|resets?\s+in)[:\s]\s*(?:for\s+)?(?:in\s+)?(\d+)\s*(hours?|minutes?|mins?|h|m)\b/i` — "try again in 5 hours", "wait 2 hours", "resets in: 3 hours". Returns `{ relative: true, waitMs }`.
3. Ambiguity flag: `ambiguous = !ampm && hour >= 1 && hour <= 12` (line 28) — a bare "resets 3" with no am/pm is flagged, and `calculateWaitMs` later resolves it by trying BOTH interpretations and picking whichever is soonest-but-still-future (or, if both already past, applying the grace-window logic below).
4. Range validation: hour>23, hour<0, minute>59, or day outside 1-31 all return `null` (lines 26, 31) rather than building an invalid Date — explicit guard against crashing on garbled TUI capture.
5. **No weekday-name parsing found** ("Monday", "next Tuesday") in time-parser.js itself — but see patterns.js's `RESET_PATTERNS` test fixture `'weekly limit resets 9am Monday'` (patterns.test.js:589) which is only used for the render-detection eligibility test (`findRateLimitMessage` returning the string), not proven to be *parsed* into a Date by `parseResetTime`. Flagging as "detected as a render but not confirmed to resolve a time" pending the corpus run.

### calculateWaitMs — fallback and reset-boundary behavior (time-parser.js:65-213)
- **Fallback on total parse failure**: `calculateWaitMs(null, marginSeconds=60, fallbackHours=5, now)` returns `(fallbackHours * 3600 + marginSeconds) * 1000` — **default fallback delay is exactly 5 hours + 60s margin** (function defaults, line 65). This is also what fires when the parsed timezone string fails `Intl.DateTimeFormat` validation (line 74-81, comment: "Invalid timezone (possibly garbled by TUI capture) — use fallback").
- **Relative time**: `waitMs + marginSeconds*1000` — a 60s margin added on top of the parsed relative delay (line 69-71).
- **Reset-boundary grace window** (`RESET_GRACE_MS = 60*60*1000`, line 63): if the parsed reset time is already in the past but by **less than 1 hour**, the code treats it as "just happened" and returns a near-zero wait (retry promptly) rather than rolling forward a full day — explicit rationale in the comment: observed live case "resets 10am" detected at 10:03 previously parked the session ~24h even though the limit had effectively cleared. Only a reset **more than** the grace window in the past rolls to the next calendar occurrence.
- **DST-safe target-timestamp resolution** (`getTargetTimestamp`, lines 101-159): builds a host-local guess Date from the target y/mo/d/h/m string, then iteratively (up to 3 passes) corrects it by rendering the guess in the target IANA timezone via `Intl.DateTimeFormat` with `hourCycle: 'h23'` (explicitly NOT `hour12: false`, because "ICU's h24 quirk can render midnight as '24:xx' paired with the previous day's date" — a specific documented gotcha) and moving by the full wall-clock delta (date included, not just time-of-day) until it converges or 3 iterations are spent.
- **Explicit DST transition-day disambiguation** (lines 143-156):
  - Spring-forward (nonexistent wall time, e.g. 2:30am on the day clocks jump 2am→3am): the iterative loop oscillates between the instants just before/after the gap; code takes `Math.max(candidate, prev)` — the LATER instant.
  - Fall-back (repeated wall time, e.g. 1:30am occurs twice): converges on the earlier occurrence by default; code detects this (`rendered(candidate + 3600_000) === targetWall`) and adds an hour to land on the LATER occurrence.
  - Both resolve to the LATE side deliberately — comment: "waking an hour late is safe, waking early finds the banner still live and burns maxRetries."
  - Tomorrow-rollover is **date-anchored** via `Date.UTC(y, mo, d+1)` normalization, explicitly NOT a flat `+24h` in milliseconds — comment states a flat +24h would wake the monitor an hour early across a fall-back transition (banner still live, burns retries) or over-wait an hour across a spring-forward.
- **Calendar-dated reset** (weekly limit with month+day, lines 165-179): anchors to that explicit calendar date rather than "today or tomorrow." Year is inferred as "the nearest occurrence at or after yesterday in tz" (so a date seen just after New Year's rolls to next year only if it's actually in the past by more than a day). If ambiguous (no am/pm) it computes both am/pm candidates and prefers whichever is still future.
- **Ambiguous bare-hour resolution outside the dated case** (lines 181-203): tries both am/pm interpretations; if both are still future, takes the sooner; if only one is future, takes that one; if BOTH are past, applies the grace check to the more-recent one, and if grace fails, rolls to the earliest (not latest) tomorrow occurrence — "otherwise we wait ~12h longer than necessary."
- **No timezone specified in the render**: falls back to `Intl.DateTimeFormat().resolvedOptions().timeZone` — i.e. the **host machine's own local timezone** (line 75), not UTC and not a "trust nothing" refusal.

## src/patterns.js (read in full — code, not test)

Context: claude-auto-retry watches a **tmux pane** (captured text, ANSI + box-drawing UI chrome), not a JSONL transcript. Its whole detection model is built around "is this rendered TUI pane, right now, showing a live limit" — very different from parsing a structured JSON transcript entry the way Limit Buster does. Much of the file's complexity is dedicated to *pane-scraping* problems we don't have (chrome/footer stripping, box-drawing, wrapped lines, tool-echo blocks) — see "For Limit Buster" for which parts still transfer.

### ANSI / chrome normalisation (patterns.js:1-18, 62-149)
- `stripAnsi()` (line 12) strips CSI (`\x1b[...`), OSC (`\x1b]...BEL/ST`), DCS (`\x1bP...ST`), and APC/SOS/PM sequences via 4 separate regexes, applied to the whole captured pane text before any line-based matching.
- `contentTailRange`/`contentTail` (140-149) trim a fixed line window (`tailLines`) from the bottom of the pane **after** stripping trailing "chrome" lines — blank lines, box-drawing borders (`CHROME_LINE` regex at line 81: `^[\s─│╭╮╰╯┌┐└┘├┤┬┴┼▏▕|]+$`), the boxed input prompt row, footer hints ("shift+tab to cycle", "? for shortcuts", version string), todo/task widget rows, spinner lines, and a usage-meter statusline row. This is pane-UI-specific; a JSONL transcript has none of this furniture.
- `toolEchoMask()` (421-431) masks out lines that are the echo of a tool call (`● Bash(grep ...` headers plus their indented/`⎿`/`└` children) so that limit-looking text quoted inside a tool's own output (e.g. a `grep` result containing the string "rate limit") isn't mistaken for a live banner. This is the single biggest false-positive guard in the file (see tool-echo.test.js below).
- Comment at line 224 explicitly notes tmux capture is called **without** `-J` (no line-joining), so wrapped lines land as separate array entries — this drives several "does this line look like a sentence continuation vs. a fresh render" heuristics (SENTENCE_END, DURATION_TAIL, etc. at 277-327).

### Limit-family patterns recognised (LIMIT_NAME_PATTERNS, patterns.js:162-170; RETRY_HINT_PATTERNS 174-176)
1. `/(?:hit|exceeded|reached).*(?:your|the)\s*(?:[\w'’-]+\s+){0,3}limit/i` — generic "hit/exceeded/reached your/the ... limit" (covers "session limit", "weekly limit", "5-hour limit", "org's monthly spend limit", etc. via the possessive-tolerant qualifier group).
2. `/\d+-hour limit/i` — explicit "5-hour limit".
3. `/limit reached/i`
4. `/usage limit/i`
5. `/out of.*usage/i` — "You're out of extra usage".
6. `/rate limit/i`
7. RETRY_HINT (separate subset, does NOT by itself vouch for a render being real): `/try again in/i`.
8. `API_LIMIT_VOCAB = /rate[_-]limit/i` (271) — the API's own underscored vocabulary (`rate_limit_error`), added only to the "names a limit" rescue set (NAMES_A_LIMIT), deliberately kept OUT of LIMIT_NAME_PATTERNS because widening that set widens `isRateLimited` itself and `rate_limit_error` shows up in source/JSON/grep output too often.
9. Spend-limit family, handled completely separately with its own shape rules (SPEND_LIMIT / SPEND_LIMIT_INDENTED, 379-390): `/you['’]ve\s+(?:hit|exceeded|reached)\s+(?:your|the)\s+(?:[\w'’-]+\s+){0,3}spend limit/i`. Tolerates curly apostrophes, boxed rendering, ⚠/· markers, emoji-presentation ⚠️. This is the one render allowed to fire with **no** reset-time anchor at all (comment 329-336) — verified instead by line-start shape + presence of the `/usage-credits` companion row + the live-region gate.
10. Interactive **menu** form (539-583): "What do you want to do? ❯ 1. Upgrade your plan / 2. Stop and wait for limit to reset" — `isRateLimitOptionsPrompt` requires the literal question, the "stop and wait" option text, AND one of "enter to confirm"/"esc to cancel"/the cursor glyph. `menuStepsToWaitOption` computes cursor-move deltas rather than assuming an option position (order varies by CLI version).
11. Overload family (585-666), fully separate from usage limits: anchored to `/\bAPI Error\b/i` line nearby + config-driven phrase patterns (comment mentions "529", "temporarily limiting requests", "overloaded_error" JSON type as examples of what callers configure). Not hardcoded strings in this file — patterns come from config (`overload.patterns`), matched via `overloadMatch`/`detectOverload`.
12. Safeguard/AUP family (672-708): "Fable 5's safeguards flagged this message (…/legal/aup)" style — also config-driven phrase patterns, anchored to nearby `API Error` line, same tool-echo mask discipline as overload.
13. Stream-interrupted / truncated-turn family (710-763): anchored to a render that **begins** the line with `API Error:` (optionally behind a message glyph) — `RENDER_HEAD = /^(?:\s*[⏺●]\s+)?API Error:/i` — NOT just "API Error nearby", because these are ordinary-English causes (dropped connection, sleep, stalled stream) that get quoted in prose easily. Scans up to 2 wrapped lines after the head.
14. Near-limit wrap-up notice (765-793), issue #78: `"Approaching your 5-hour usage limit — Claude will wrap up the current step."` — NOT a limit-hit render; it's an early warning printed ~95% into the window with no reset banner. Detected via `WRAP_UP_HEAD` line-start anchor; dedup logic walks bottom-up and stops at the first user input row below the notice (meaning: already handled/responded to).

### Reset-time-bearing shapes recognised at the pattern layer (RESET_PATTERNS, patterns.js:181-190)
- `/resets?\s+(?:at\s+)?\d{1,2}(?::\d{2})?\s*(?:am|pm)?/i` — "resets 3pm" / "resets at 3:00 PM".
- Month-name + day + time: `resets (on )?<MONTH> \d{1,2}(st|nd|rd|th)?,? (at )?\d{1,2}(:\d{2})? (am|pm)?` — e.g. "resets Aug 21 at 3pm". MONTH regex (180) covers jan/feb/mar/.../dec plus "sept", with optional trailing `.` and shared textually with time-parser.js's own month regex (comment says "shared with time-parser.js's clause regex" — worth double-checking they're literally the same string, not just conceptually).
- `/resets?\s+in[:\s]\s*\d/i` — "resets in: 3 hours".
- `/try again in \d+\s*(?:hours?|minutes?|h|m)/i` — "try again in 5 hours".
- These are just the "does this line carry a reset-shaped clause" patterns; the actual date/time parsing/normalisation into a Date lives in time-parser.js (not yet read).

### Render-vs-prose disambiguation ("#73" system, patterns.js:192-327)
This is the most novel piece of engineering in the file, worth calling out on its own for the design ideas even though it's pane-specific:
- Problem: a line can *mention* a limit/reset without *being* a live banner (model prose discussing it, a user's own question, a stale banner sitting above newer scrollback).
- `presentsResetTime(line)` treats "named a limit" as a **rescue that outranks everything else** (checked first, after only the prompt-glyph absolute veto for the user's own input row). Three demotion signals (bullet-glyph-without-clause, sentence-final punctuation, reset clause followed by >2 non-parenthetical words) only apply to lines that do NOT already name a limit — because the authors found via 3 earlier failed revisions that demoting on those signals alone would demote real renders that happened to end in a period or carry an inline hint.
- Explicit asymmetric-cost reasoning documented in comments (230-239): under-waiting self-corrects on next check; over-waiting (locking onto a stale banner) is "unrecoverable until the wait expires" given a described latch mechanism (`#70`) that only revisits *fallback* waits, not parsed ones. This design principle (bias false-negatives over false-positives on reset-time parsing, but only where an independent recheck loop exists) is a takeaway worth flagging for Limit Buster's own scheduler.
- `findRateLimitMessage` (826-882) scans **bottom-up** (most recent = truthful) through three fallback tiers: (1) lines that `presentsResetTime`, (2) any line matching a raw `RESET_PATTERNS` shape (pre-#73 behavior, for when everything got vetoed as prose), (3) any line matching `LIMIT_PATTERNS` at all with no reset (this is where the spend-limit banner, which never carries a reset, gets caught).

### Ranking / disambiguation mechanism overall
There is no numeric scoring/confidence system. Disambiguation is entirely rule-based and ORDER-dependent:
1. Absolute veto: prompt-glyph (user's own input) lines are never renders.
2. Rescue: any line naming a limit (by the LIMIT_NAME_PATTERNS/API_LIMIT_VOCAB set) is treated as a real render regardless of other signals.
3. Otherwise: bullet-without-clause, sentence-end punctuation, or a long tail after the reset clause demote the line to "prose."
4. Search direction is always bottom-up (freshest wins) with a chrome-aware + tool-echo-aware line window bounding how far up the scan can reach.
5. Family-specific detectors (overload/safeguard/stream-interrupted) each require an `API Error`-anchored line within a small window (`WINDOW = 6` lines, or 2-line wrap window for stream-interrupted) rather than a bare phrase match anywhere in the capture.

Every detector accepts a `tailLines` (or fixed `OVERLOAD_TAIL_LINES=12`/`OVERLOAD_MAX_RAW_LINES=20`/`WRAP_UP_TAIL_LINES=40`) window parameter — 0 means "scan everything" and is used only for print-mode (piped process output) rather than a live scrolling TUI pane.

## For Limit Buster

Ranked concrete takeaways. Each states its evidence (code read / test read / direct execution against our own compiled parser) and the file(s) in our repo it would touch.

### Adopt

1. **Reset-boundary grace window for a just-passed reset time.** *(Evidence: code read of `time-parser.js:50-63` + `calculateWaitMs:181-212`; pinned by 3 dedicated tests in `time-parser.test.js:167-194` reproducing a real incident — "resets 10am" detected at 10:03 previously waited 86273s/~24h.)* Our `nextZonedOccurrence` (`src/parsers/limitParser.ts:210-224`) walks forward from *today* and returns the first day-offset whose instant is still `> now` — with no grace period, a reset that passed 3 minutes ago rolls a full 24h forward exactly like the bug claude-auto-retry documents fixing. This is a **verified-plausible gap in our own code**, not just a nice-to-have: I did not find any grace-window logic in `limitParser.ts` or a corresponding test in `test/parsers/limitParser.test.ts` (grep for "grace" turned up nothing). Touches `src/parsers/limitParser.ts` (`nextZonedOccurrence` / `resolveClockTime`) — add a ~1h grace check before rolling to the next day-offset, mirroring `RESET_GRACE_MS`.
2. **Calendar-dated reset parsing** ("resets Oct 3, 9am", "resets Aug 21 at 3pm (Australia/Brisbane)"). *(Evidence: fixture table above, verified by direct execution — our `detectLimit` returns `undefined` resumeAt for both weekly-dated fixtures despite recognising them as limit-shaped; their `time-parser.js:1-6,161-179` + 6 dedicated tests in `time-parser.test.js:197-234` handle this, including year-inference across a Dec→Jan boundary.)* Weekly limits are a real Claude Code render (their comment cites "a real Claude Code record, PR #56's fixture"); our repo has zero handling for a month name anywhere in `RULES`. Touches `src/parsers/limitParser.ts` (new `RULES` entry + a `resolveCalendarDate`-style function alongside the existing `resolveClockTime`).
3. **Tool-echo false positive fix for untrusted candidates.** *(Evidence: direct execution against our own `out/src/parsers/limitParser.js` — a `grep` argument quoting a real limit banner is detected as a live limit with a resolved resume time, `trusted: false`; this is the exact shape of their dated, real incident #63, independently reproduced against our code.)* This is the single highest-value finding in this slice: it is a **verified bug in our own repo**, not merely "their tool handles X and we don't." Their fix (`toolEchoMask`, patterns.js:404-431) is TUI-scraping-specific and not directly portable, but the underlying idea transfers cleanly to our JSONL model: `collectStrings()` (`src/transcriptWatcher.ts:500-520`) should stop walking into (or should tag as untrusted-even-more-strictly) values found under a tool-call's own input/argument fields (e.g. a Bash `command`, a Grep `pattern`) and under a tool-result's raw content — those are text a tool merely **echoed**, structurally distinguishable in JSONL (unlike a scraped pane) by which field of the entry object they came from. Touches `src/transcriptWatcher.ts` (`collectStrings`, and/or the call site at line 392-419) and needs a new test in `test/transcriptWatcher.test.ts` mirroring their `tool-echo.test.js` fixtures (none currently exists — confirmed by grep).
4. **Terminal-vs-in-flight-retry distinction for overload.** *(Evidence: direct execution — our `overloadParser.detectOverload` treats `"API Error (529 {...}) · Retrying in 5s · attempt 3/10"` identically to a terminal `"API Error: 529 Overloaded"`; their `overload.test.js:83-85` explicitly tests this as a MUST-NOT-fire case, with the stated rationale "Acting on it would interrupt Claude's own backoff.")* Whether this is exploitable in our architecture (does a JSONL entry ever carry the in-flight-retry rendering before the turn settles?) was not established in this slice — DETECTION only, no read of transcriptWatcher's polling/timing. Still worth a cheap defensive regex exclusion in `src/parsers/overloadParser.ts` (`RULES`'s `api-error-status`, line 60-63) for the literal `Retrying in` / `attempt N/M` suffix, since the cost of adding it is near zero and the downside of not having it (per `src/policy.ts:38-43`, ANY overload detection schedules a real resume) is a spurious `claude --resume` into a session still mid-turn.
5. **"Temporarily limiting requests (not your usage limit)" 429 render should route to overload, not fall through both parsers.** *(Evidence: direct execution — confirmed above under "Three gaps"; the message's own text explicitly disclaims being a usage limit, and it is currently silently dropped by both our parsers.)* Their fix is structural: `looksLikeOverloadMessage`'s "a 429 belongs to the limit parser" carve-out (`overloadParser.ts:51-53`) needs a counter-exception for this literal phrase (or: only let `rate limit` vocabulary claim a message for the limit parser when a reset-time-shaped clause is also nearby, closer to how claude-auto-retry's own overload/limit split works). Touches `src/parsers/overloadParser.ts:46-55` and/or `src/parsers/limitParser.ts:49-63` (`LIMIT_HINTS`).

This is presented as "consider" rather than "adopt" because I did not verify the downstream behavior in `src/scheduler.ts` — flagged as a lead for whoever reads `src/scheduler.ts`, not a confirmed gap.
7. **Bare `try again in` / bare "out of ... usage" as standalone limit signals**, even with no other limit vocabulary in the sentence (fixture table rows 3 and 4). *(Evidence: direct execution — our `LIMIT_HINTS` rejects both `"You're out of extra usage · resets 3pm"` and `"Please try again in 5 hours"` outright.)* Lower priority than the "Adopt" items because these are terse, API-only phrasings less likely to appear as-is in a real Claude Code JSONL entry (their fixtures are captured from a TUI pane, where terse renders are more common than in the structured error fields we read) — but cheap to add to `LIMIT_HINTS` if a real transcript sample surfaces either phrasing.
8. **The asymmetric-cost design principle** documented at length in patterns.js:230-239 ("under-waiting self-corrects... over-waiting is unrecoverable until the wait expires... every signal is therefore only ever evidence of prose") is a reusable engineering idea independent of any specific regex: when a detector must choose between two error directions and only one has a recheck loop behind it, bias toward the recoverable one. *(Evidence: code comment + corroborated by ~20 pinned test cases in patterns.test.js.)* Worth keeping in mind for any future disambiguation logic in `src/parsers/limitParser.ts` or `src/scheduler.ts`, even though it's a principle rather than a portable code change.

### Avoid

9. **Do not port the pane-scraping machinery wholesale** — `stripAnsi`'s CSI/OSC/DCS/APC-SOS-PM handling, chrome-line stripping (`CHROME_LINE`, box-drawing detection, footer/spinner/todo-widget anchoring), the tool-echo header/result mask, the bottom-up-freshness scan, the prompt-glyph/bullet/sentence-punctuation render-vs-prose veto system (`#73`), and the interactive `/rate-limit-options` menu navigation (cursor-step counting). *(Evidence: all of this is explicitly a response to scraping a **live scrolling tmux pane** — comments throughout patterns.js are explicit about this, e.g. "tmux capture-pane is called without -J", "a live banner sits ABOVE this chrome... pushed well up the pane.")* None of it applies to a JSONL transcript, which has no chrome, no scrollback-vs-live-region distinction, no wrapped lines, and no box-drawing. Our existing structured-field trust gate (`isRateLimitEntry`/`isApiErrorEntry`) already gets most of the *benefit* this machinery exists to provide, for free, which is the same conclusion `docs/PRIOR-ART.md` already reached about a different prior-art repo — this slice just adds a second, independent confirmation of it from a much more elaborate codebase.
10. **Do not adopt the interactive-menu-navigation feature** (`isRateLimitOptionsPrompt`/`menuStepsToWaitOption`, patterns.js:539-583) — it exists because claude-auto-retry drives an interactive terminal and must choose a menu option with arrow keys. We never interact with a live terminal UI; our `resumer.ts` spawns `claude --resume <uuid> "Continue where you left off."` as argv with no shell (per the brief), so there is no menu to navigate in the first place.
11. **Do not adopt the "StopFailure" hook/event-marker channel** referenced throughout `overload.test.js` (a second, non-text detection channel apparently fed by an installed Claude Code hook) — out of scope for a text/JSONL-detection comparison, not something this slice investigated, and appears to be a companion mechanism specific to their tmux/hook integration rather than something a JSONL watcher could read the same way.
