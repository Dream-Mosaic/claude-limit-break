## panel.ps1 and web/index.html

**panel.ps1** (580 lines) is a pure-PowerShell `System.Net.HttpListener` web server, no external web framework, serving `web/index.html` and a small JSON API, documented in its own header comment (panel.ps1:5-21):
- `GET /` -> web/index.html
- `GET /api/status` -> `{preheat:{tasks}}`, cached in-process (`$PreheatStatusCacheTtlSec`) so polling doesn't shell out to `preheat.ps1`/Task Scheduler on every request (panel.ps1:152-154, 237-259) — falls back to stale cache rather than a blank response if a live query fails.
- `GET /api/schedule` -> `{rules:[...], mtime:"<ticks>"}` — the mtime is an optimistic-lock token (see below).
- `GET /api/ratelimits` -> the cached usage windows written by statusline-tap.cjs (i.e. reads `state-ratelimits.json`, confirms the panel quota strip's data source).
- `GET /api/learn` -> the 30-day rhythm + 7-day utilization report, computed in-process (not by shelling out — confirmed by a test title "the panel computes the rhythm report in-process, not by shelling out").
- `POST /api/preheat/once` -> `{kind:"reset"|"at"|"plus", value:...}`, schedules a one-shot.
- `POST /api/preheat/apply` -> `{rules:[...], baseMtime?}`, rewrites schedule.json and re-registers tasks; `baseMtime` is an **optimistic-concurrency lock** — a stale `baseMtime` gets rejected with 409 (confirmed by test.ps1 title "POST /api/preheat/apply refuses a stale baseMtime -> 409"), preventing two browser tabs/panel instances from silently clobbering each other's schedule edits.

**POST security gate** (`Test-PostSecurity`, panel.ps1:200-233, labeled "Finding 7" in a comment, implying this came out of a security review): every POST must (1) have `Content-Type: application/json` (blocks simple HTML form POSTs, a classic CSRF vector), (2) have an `Origin`/`Referer` header, if present, starting with `http://localhost:`, `http://127.0.0.1:`, or `http://[::1]:` only, (3) come from a loopback `RemoteEndPoint` address (`IPAddress.IsLoopback`). No auth token — matches SECURITY.md's stated "single-user assumption" (any local process running as the same user can drive the panel). This is exactly the CSRF-without-auth model documented in SECURITY.md, now confirmed in code.

**Singleton/port-guard logic** (panel.ps1:480-531): before binding port 7878, checks if the port is already listening (`Get-NetTCPConnection` on Windows, `lsof` on macOS), and if so, probes `GET /api/status` to distinguish "another instance of this same panel is already up" (message: "panel is probably running; open <url>") from "some unrelated program is squatting on 7878" (message: "port is in use by another program... start with -Port <another port>"), explicitly choosing to assume it's a legitimate second run rather than misdirect the user to a strange app if the probe times out (e.g. during a slow `apply`). Retries the actual `HttpListener.Start()` bind up to 3 times with a 3s backoff for a port that "can linger briefly after a killed instance."

**web/index.html** (911 lines, single-file HTML/CSS/JS, skimmed not fully read): confirms the panel.png screenshot's structure in code — a `LANG` variable persisted to `localStorage` (`clr_lang`), default `'zh'` (Chinese) unless explicitly set to `'en'` (`web/index.html:273`), full `zh`/`en` string tables (`web/index.html:275`,`307`), `<html lang="zh-CN">` by default (index.html:2). The one-shot UI wires a native `<input type="time">` and proactively calls `.showPicker()` on click (index.html:538, comment: "pop the clock picker right away"). Schedule edits round-trip a `schedMtime` value and only include `baseMtime` in the apply POST body "when we never got one" is omitted — confirms the optimistic-lock flow end-to-end (index.html:841-842, comment: "omit the lock token when we never got one - better to write than to 409 forever").

## install.ps1, platform.ps1, run-hidden.vbs, schedule.example.json — scheduling and system changes

**Complete list of changes claude-preheat makes to the user's system (compiled from install.ps1 + platform.ps1, both read in full):**
1. **PowerShell profile** (`$PROFILE.CurrentUserAllHosts`): appends a marker-delimited block (`# >>> claude-preheat functions >>>` ... `# <<< claude-preheat functions <<<`) defining two functions, `preheat` and `claude-panel`, each a thin wrapper (`& '<repoDir>/preheat.ps1' @args`) (install.ps1:96-136). Idempotent (skips if byte-identical block already present) and self-migrating (strips an old v0.2 `claude-limit-relay` block first). A timestamped `.bak-<timestamp>` copy of the profile is written before any edit (install.ps1:112-116). Considerable defensive encoding-sniffing logic (BOM detection for UTF-8/16/32, ANSI codepage fallback) to avoid mojibake-ing a non-ASCII profile (install.ps1:47-91) — this is the single most defensive/paranoid piece of code in the repo, evidence of prior real-world bug reports.
2. **Windows Task Scheduler**: per-user scheduled tasks named `ClaudePreheat-Wk-*` (weekly) and `ClaudePreheat-Once-*` (one-shot), registered via `Register-ScheduledTask` with NO elevation (platform.ps1:262-293). Action is `wscript.exe //B //Nologo run-hidden.vbs "<pwsh>" -NoProfile -ExecutionPolicy Bypass -File preheat.ps1 fire` (platform.ps1:238-243) — i.e., every fire runs with `-ExecutionPolicy Bypass` scoped to that single process invocation only (does not change the user's persisted execution policy). Task settings (platform.ps1:245-257): `AllowStartIfOnBatteries=$true`, `DontStopIfGoingOnBatteries=$true` (explicitly runs on battery, changed from an earlier version per README note #5), `ExecutionTimeLimit=30min`, `MultipleInstances='IgnoreNew'`, `WakeToRun=$true` UNLESS it's a `-NoWake` (chase) job. Deliberately does NOT set `-StartWhenAvailable`, so a missed fire (PC off) is simply skipped, not replayed at next logon — explicit reasoning in-code: "a missed fire replayed at logon would anchor the 5h window at that moment, which is worse than skipping it" (platform.ps1:249-251). Runs as "Interactive logon type" — fires only while the user is logged in (locked screen OK, signed-out skipped).
3. **macOS launchd**: per-user LaunchAgent plists at `~/Library/LaunchAgents/com.claude-preheat.*.plist` (platform.ps1:35,262-273), loaded via `launchctl bootout` (idempotent unload) then `launchctl bootstrap gui/<uid> <plist>` with a 3x retry against a transient "already loaded" race (platform.ps1:275-284). Each plist embeds a `StartCalendarInterval` (weekly: one dict per weekday with Hour/Minute; one-shot: a specific Month/Day/Hour/Minute), the full `ProgramArguments` array invoking `pwsh -NoProfile -File preheat.ps1 fire`, a snapshotted `PATH` env var (so the job can find `claude`/`node` the same as an interactive shell — platform.ps1:211-212,227-228), and `StandardErrorPath` pointed at `launchd-err.log` in the repo dir.
4. **macOS shims**: `~/.local/bin/preheat` and `~/.local/bin/claude-panel`, one-line bash scripts that `exec` the resolved `pwsh` binary against the corresponding `.ps1` (install.ps1:158-173). Warns (does not auto-edit) if `~/.local/bin` isn't on PATH.
5. **Local files inside the repo directory only** (per SECURITY.md, confirmed by preheat.ps1 path constants): `schedule.json` (copied from `schedule.example.json` on first install if absent — install.ps1:14-26), `state.json`, `preheat-log.jsonl`, `state-ratelimits.json`, `.fire.lock`, `firepit/` (empty scratch dir), `launchd-err.log` (macOS only).
6. **Claude Code's own settings file** (`~/.claude/settings.local.json` or `~/.claude/settings.json`), ONLY if the user runs `preheat statusline on`: wraps or sets the `statusLine.command` field to pipe through `statusline-tap.cjs` (preheat.ps1:1021-1149, detailed above). Backed up with a timestamp before every write, plus a `statusline-original.json` sidecar for exact restoration. This is the one place the tool touches Claude Code's own configuration, and it's opt-in, not part of default `install.ps1`/`apply`.
7. **One legacy cleanup**: on Windows, if upgrading from v0.2, removes the old `ClaudeRelay-Probe` scheduled task (install.ps1:143-149) — the only case where it removes something not of its own current creation.
8. **Nothing else**: no registry writes found, no elevation/admin prompts (explicitly "no admin rights needed" per README, matches: Task Scheduler tasks registered per-user without `-Principal`/elevation flags in platform.ps1), no services installed, no startup-folder entries observed in the files read. install.ps1 also checks (but does not silently fix) the user's persisted PowerShell execution policy, warning if `Restricted`/`AllSigned`/`Undefined` would prevent the profile (and thus the `preheat`/`claude-panel` functions) from loading (install.ps1:192-208) — a read-only check, not a `Set-ExecutionPolicy` call.

**Hidden execution — `run-hidden.vbs` (full file, 31 lines, Windows only):** a WScript shim whose sole purpose is to invoke the real command via `WScript.Shell.Run(cmd, 0, True)` — window style `0` = hidden, `bWaitOnReturn = True` = synchronous, blocks until the child exits and returns its exit code. In-code comments explain three prior bugs this design fixes (run-hidden.vbs:1-11): (a) a plain console Task Scheduler action flashed a visible cmd window on every fire; (b) using an S4U (non-interactive) task principal would also hide the window but would silently break BurntToast notifications, so they kept it interactive + used this VBS wrapper instead; (c) an earlier fire-and-forget version made Task Scheduler think each fire finished in milliseconds, which broke `ExecutionTimeLimit`/`MultipleInstances` enforcement (applied to the shim, not the real long-running pwsh) and let a just-woken machine be judged idle and put back to sleep mid-retry. Also fails loudly (`WScript.Quit 127`) if a path-qualified target binary doesn't exist, fixing a prior bug where a deleted `pwsh.exe` (e.g. after a Microsoft Store auto-update) silently reported exit 0 with nothing having run, making Task Scheduler show a false-green history (run-hidden.vbs:16-24).

**Sleep/wake handling, summarized (from platform.ps1:413-441, matches and extends README/MAC-BETA claims):**
- Windows: `Test-WakeTimers` runs `powercfg /query SCHEME_CURRENT SUB_SLEEP RTCWAKE` and warns (does not auto-fix) if wake timers are disabled (`0x00000000`) or set to "important only" (`0x00000002`) on the active power plan. This is what backs the "PC can be woken to fire" claim — it's conditional on this OS setting, which the tool only reads, never changes.
- macOS: `Test-WakeTimers` runs `pmset -g`, parses the `sleep` idle-timeout line, and warns if system sleep is enabled at all, since (asserted, and consistent with launchd's documented lack of a wake-from-sleep mechanism) "launchd cannot wake a sleeping Mac." Again read-only, no `pmset` write.
- Notifications: Windows uses optional BurntToast (`New-BurntToastNotification`, only if module is present — platform.ps1:466-469); macOS uses native `osascript display notification` (platform.ps1:462-464, no extra install needed, matches MAC-BETA.md:64).
- `Send-Toast` (platform.ps1:443-470) messages are literal and distinguish: success+new-anchor ("window preheated - new 5h window anchored"), success+already-running ("ping landed in a running window - anchor unchanged"), auth failure ("preheat FAILED - Claude login expired? run: claude"), limit failure ("preheat skipped - usage limit already hit, nothing to preheat until it resets"), and a chase booking appended as extra text ("window busy - follow-up preheat at HH:mm").



## preheat.ps1 (read directly, source of truth over the docs above)

Repo root: `$Root = $PSScriptRoot`. Key paths (preheat.ps1:37-46): `schedule.json`, `state.json`, `preheat-log.jsonl`, `firepit/` (scratch cwd for the ping), `mcp-empty.json`, `.fire.lock`. Scheduled-task name prefixes `ClaudePreheat-Wk*` / `ClaudePreheat-Once*`. `$WindowHours = 5` is a hardcoded constant used everywhere below.

**Exact claude invocation, confirmed in code (preheat.ps1:605), matches and extends the SECURITY.md doc claim:**
```
-p "hi" --model haiku --no-session-persistence --strict-mcp-config --mcp-config "<path to mcp-empty.json>" --output-format json
```
Run via `Start-Process -FilePath $claude -ArgumentList $pingArgs -WorkingDirectory $FirePit -RedirectStandardOutput ... -RedirectStandardError ... -PassThru -NoNewWindow` (preheat.ps1:615-616), a 240-second timeout with `$p.Kill()` on timeout (preheat.ps1:618-620).

**How it keeps cost minimal (all in code, preheat.ps1:605):**
- `--model haiku`, cheapest model.
- `-p "hi"`, a two-character prompt, one-shot non-interactive (`-p`/print mode, no back-and-forth).
- `--mcp-config mcp-empty.json` + `--strict-mcp-config`, forces zero MCP servers for this invocation regardless of the user's normal project/global MCP config, so no MCP server startup cost or tool-list injection into context. This confirms the earlier guess about mcp-empty.json's purpose.
- `--output-format json`, structured single JSON object, machine-parseable, avoids interactive UI rendering.

**How it avoids polluting `~/.claude/projects` (the flag that directly answers the brief's question), preheat.ps1:605 and comment at preheat.ps1:362-363:**
- The flag `--no-session-persistence` is passed. Code comment (preheat.ps1:362-363): "the ping runs in firepit/ and leaves no transcript, so only the journal knows." This is a direct claim, from a code comment (not doc marketing), that this flag suppresses transcript/session-file writes to `~/.claude/projects`.
- Additionally, `-WorkingDirectory $FirePit` runs the process cwd inside `firepit/`, an empty scratch directory inside the repo (confirmed at SECURITY.md:20-22 and preheat.ps1:41,585-588), which is a belt-and-suspenders move: even if a project-scoped transcript were written, it would be scoped to that empty throwaway directory rather than the user's real project, and per SECURITY.md the ping therefore "never sees your code."
- Net effect: **we did not find evidence in this repo of `~/.claude/projects` inspection for POLLUTION (only for READING, see Get-LastLocalActivity below), which is consistent with `--no-session-persistence` doing its job of not writing a transcript at all.** This is asserted by their code comment; we have not independently verified against Claude Code's own source/docs that `--no-session-persistence` suppresses `~/.claude/projects/*.jsonl` writes — flag as asserted-in-comment, not independently verified by us.
- **This is directly relevant to Limit Buster**: our `resumer.ts` opens a VS Code terminal running `claude --resume <uuid> "Continue..."` — a full resume, which is supposed to create/continue a transcript (that's the point). But if Limit Buster ever needs a "probe" or "test" invocation of `claude` (e.g. to check auth, or a lighter-weight signal), `--no-session-persistence` + `--strict-mcp-config --mcp-config <empty>` is the documented-by-example recipe for a footprint-free call.

**Payload/verdict parsing — `Test-PingOutput` (preheat.ps1:516-555), pure function, unit-testable without spending a token:**
- Parses stdout as JSON FIRST regardless of exit code, because "a usage-limit hit exits 1 with the reason in `result` and nothing on stderr" (preheat.ps1:523-526) — i.e., the `claude -p --output-format json` payload can carry `is_error: true` with the failure reason in `.result`, distinct from a shell-level nonzero exit.
- Classifies failures into `kind = 'auth' | 'limit' | 'other'` by regex over the error text: auth = `not logged in|log ?in|authenticat|unauthori[sz]ed|expired|invalid api key|oauth` (case-insensitive); limit = `usage limit|session limit|rate.?limit|limit reached|hit your limit` (preheat.ps1:550-551). **These are the literal user-facing substrings claude-preheat treats as authoritative limit/auth signals** — comparable ground to our own `limitParser.ts`/`overloadParser.ts` regexes, worth a direct diff.
- On success, reads `total_cost_usd` from the JSON payload as `$cost` (preheat.ps1:543) — i.e. Claude Code's own `-p --output-format json` mode reports actual USD cost per invocation; this is a ready-made per-call cost readout that our `budget.ts` could use instead of estimating.

**Retry logic (preheat.ps1:606-648):** up to 3 attempts. Breaks immediately (no more retries) if the failure kind is `auth` or `limit` — "neither an expired login nor a usage limit heals in 90s" (preheat.ps1:637-638). Otherwise sleeps 90s between attempts and self-heals a stale cached `claude` binary path via `Resolve-ClaudeExe -NoCache` after the first failed attempt (handles e.g. a CLI reinstall that moved the binary).

**Fire lock (preheat.ps1:560-581, `.fire.lock`):** a concurrency guard so two near-simultaneous scheduled fires (e.g. a weekly + a chase landing the same minute) don't double-ping. Lock file holds `{pid, job, startedAt}`; a lock is considered "theirs" (respected, not stolen) only if it's under 20 minutes old AND that PID's process is still actually running (`Get-Process -Id ...`) — otherwise treated as stale and overwritten. Best-effort: failure to write/delete the lock must "never cost the ping" (preheat.ps1:561-563).

**Anchor/window model — this is the core "5-hour window" logic, and it is important to note NONE of it calls any Anthropic API to ask "is a window open"; it is entirely local inference from three signals:**
1. `Get-LastLocalActivity` (preheat.ps1:324-343): scans the **20 newest-by-mtime `*.jsonl` files under `~/.claude/projects` (recursive)**, and for each, reads the **last 2MB** of the file (preheat.ps1:306) looking for the newest line matching `"type":"assistant"` or `"type":"user"` with a `"timestamp"` field (regex, not a JSON parse — preheat.ps1:314-317), returns the max such timestamp converted to local time. Explicit code comments call out two traps this design avoids (preheat.ps1:294-301): (a) file mtime can be bumped by indexers/backups without real content changes, so mtime alone is untrustworthy; (b) not every appended record is a real API turn — Claude Code also appends `attachment`/`away_summary`/`turn_duration`/`stop_hook_summary` bookkeeping records to an open-but-idle session, so "the file grew" != "the model was called" != "a window was anchored." **This is a substantive, tested (see test.ps1 later) claim about Claude Code transcript internals that's directly relevant to our own `limitParser`/`stallWatch` — worth checking whether our transcript-tailing logic already accounts for these bookkeeping record types or could false-positive on them.**
2. `Get-KnownWindowEnd` (preheat.ps1:345-358): reads `state-ratelimits.json` (written by statusline-tap.cjs) for `rate_limits.five_hour.resets_at` (Unix seconds), i.e. the EXACT window-end time as last reported by Claude Code's own statusline payload — used when available, since it's authoritative vs. the estimate from #1. Returns `$null` if the tap isn't installed.
3. `Get-LastPreheatAnchor` / `Test-RecentPreheatAnchor` (preheat.ps1:404-442): the tool's OWN journal (`preheat-log.jsonl`) of past successful+anchored pings, since a preheat ping itself "leaves no transcript" (see above) and so is invisible to signal #1.

`Test-FreshAnchor` (preheat.ps1:360-374) combines all three to decide, after a ping, whether it actually opened a NEW window (`anchored = true`) or landed inside one already running (`anchored = false`): false if a preheat of our own anchored one within the last 5h (self-chain guard); true if there's no local activity at all; true if the fire is ≥5h (UTC) after the last local activity; true if the tap's known window END was before the fire AND no activity happened after that end. Comment flags a real limitation: "Blind to phone/web use, like every local observation" (preheat.ps1:367) and DST: "a local-time gap that straddles a DST switch is off by an hour" (preheat.ps1:369) — window-length math is UTC-normalized specifically to dodge that, per the code.

**Chase / follow-up mechanism (preheat.ps1:462-503, `Get-ChasePlan`/`Invoke-Chase`):** if a *scheduled* fire lands inside a window that's already running (i.e. it failed to anchor a fresh one), the tool computes the running window's expiry (`$end`) — from the statusline tap's exact `resets_at` if fresh enough, else ESTIMATED as `$LastAct + 5h` (preheat.ps1:475-477, explicitly labeled `source: 'estimate'` vs `'ratelimits'`) — and schedules ONE follow-up ping for 2 minutes after that expiry (preheat.ps1:478-481, "two whole minutes, not 60s: resets_at is truncated to the minute, so a +60s chase could still land a second inside the old window"). Guards against infinite chase chains: skipped entirely if a preheat already anchored the currently-running window (`RecentAnchor`) or if the next regularly-scheduled weekly fire would come first anyway (within 5 min, preheat.ps1:482-484). The chase's own scheduled fire is registered `-NoWake` (preheat.ps1:500-502) — explicitly must NOT wake a sleeping PC "at a minute the user did not choose," unlike the user's chosen weekly fires which do get wake timers.

**`learn` command (preheat.ps1:823-938):** reads `~/.claude/history.jsonl` (NOT the projects transcripts — "the cheapest full activity record there is," preheat.ps1:826-828), one line per user prompt with an epoch-ms timestamp, filtered to last 30 days. `Get-WindowStats` (preheat.ps1:846-861) reconstructs 5h windows from raw prompt timestamps using the exact same anchor rule stated in the README: "the first prompt while no window is active opens one; everything within 5h of the anchor rides it; the next prompt after expiry anchors the next" (preheat.ps1:847-849) — this is the tool's own from-scratch reimplementation of the window model, used only for the `learn` heuristic, not for real-time decisions. Per-weekday median session-start time is computed, and the suggested reset time is `median + 60 minutes, rounded to nearest 30 min` (preheat.ps1:886-888, comment: "early work rides the old window's tail, the bulk of the session gets a fresh one" — i.e. an asserted heuristic, not a hard rule). Also computes a 7-day "window utilization" estimate (engaged-hours / total-window-hours, with a 30-min grace period added per window to account for agent runs that under-count in prompt-only data) — explicitly labeled "ESTIMATE" in a comment (preheat.ps1:900-901).

**`statusline on|off` wiring (preheat.ps1:1021-1149, `Invoke-StatusLineSetup`):** installs `statusline-tap.cjs` as a transparent pipe stage in front of the user's EXISTING Claude Code `statusLine.command` (in `~/.claude/settings.local.json` or `settings.json`), producing `"<node>" "<tap-path>" | ( <original command> )`, or, if the user had no statusLine configured, `"<node>" "<tap-path>" --solo` so the tap renders a minimal line itself. Explicitly billed as "a pure pipe stage" that forwards stdin byte-identical to stdout so wrapping "is safe for ANY existing command" (preheat.ps1:1022-1025, matches statusline-tap.cjs:2-5). Writes a timestamped backup of the settings file plus a `statusline-original.json` sidecar recording exactly which file/command was wrapped, so `off` restores precisely (falls back to unwrapping via regex on the wrapper command string if the sidecar is missing, and refuses to touch anything if it can't confidently restore — preheat.ps1:1080-1091). `off` checks BOTH `settings.local.json` and `settings.json` for the tap (a fix noted in-code as "found by review 2026-08-15," preheat.ps1:1046-1049) so a tap in the "other" file isn't silently orphaned.

## statusline-tap.cjs (full file, 82 lines, read directly — this directly answers the brief's "better signal source" question)

**What it is:** a Node.js CommonJS script installed as (or chained in front of) the Claude Code `statusLine` command. Claude Code invokes the configured `statusLine.command` on every statusline render and pipes a JSON payload to its **stdin**; the tap reads all of stdin, tries to `JSON.parse` it, and — critically — **re-emits the exact same bytes to stdout unchanged** (statusline-tap.cjs:21-25,51-52) so whatever the user's real statusline renderer was continues to work identically; this is what the code calls a "transparent pipe stage."

**What fields it reads, and where they come from (statusline-tap.cjs:27,55-79):** from the parsed JSON payload that Claude Code itself feeds to the statusLine command on stdin —
- `payload.model.display_name` (model name, used only in `--solo` rendering)
- `payload.rate_limits.five_hour` — an object with `.utilization` (preferred) or `.used_percentage` (fallback) as a numeric percent, and `.resets_at` (epoch seconds or ms, auto-detected via `v > 1e12` heuristic at statusline-tap.cjs:57)
- `payload.rate_limits.seven_day` — same shape, described as the "weekly" window in the README/panel

Comment at statusline-tap.cjs:6-9 explicitly calls this "the only documented machine-readable source of the 5h/weekly usage windows" available to them — i.e., the CLAIM (asserted by the tool author, not verified by us against Anthropic's own docs) is that Claude Code's `statusLine` command hook is the one place the CLI exposes exact, structured `rate_limits` data (utilization % + exact reset timestamp for both the 5-hour and weekly/7-day windows), as opposed to the free-text limit messages that appear in transcripts/API errors.

**Side effect / where the data lands:** on every render where `payload.rate_limits` is present, the tap atomically writes `{capturedAt: <ISO now>, rate_limits: payload.rate_limits}` to `state-ratelimits.json` next to itself, using open+write+fsync+rename for durability (statusline-tap.cjs:28-48, comment explains a naive rename-without-fsync left a zero-length cache behind a crash). This file is then read by `Get-KnownWindowEnd` in preheat.ps1 (see above) and by panel.ps1 for the live quota strip shown in docs/panel.png ("from statusline cache · 1 min ago").

**`--solo` mode** (statusline-tap.cjs:19,51,64-81): if invoked with no downstream statusline configured, instead of forwarding raw JSON it renders a minimal human-readable line itself, e.g. `Sonnet 5h 62%→14:52 · wk 38%→10:50`, using the same `rate_limits` fields.

**Assessment for Limit Buster (flagged here, expanded in the final section):** this is a genuinely different signal channel than transcript-text parsing — it's a small amount of structured JSON (`rate_limits.five_hour.{utilization,resets_at}`, `rate_limits.seven_day.{utilization,resets_at}`) that Claude Code itself pushes on every statusline render, if the user has (or is given) a `statusLine` command configured. It does NOT require watching `~/.claude/projects/*.jsonl` or regex-matching limit error text at all. The catch: it is push-based and passive — it only updates when Claude Code renders the statusline (i.e., during an active session), so it cannot proactively tell you a window has reset while no session is open, the same limitation preheat.ps1 works around with its separate local-activity/journal heuristics above.

## For Limit Buster

### Could "preheat" work as a Limit Buster feature?

Technically yes — the mechanism is small and well-tested (evidenced: `preheat.ps1:605`, `.github/workflows/e2e-mac.ps1` argv assertion). The core idea, a scheduled cheap ping that anchors the 5h window at a chosen time, is orthogonal to what Limit Buster does today (Limit Buster is reactive: it waits for a real limit hit and resumes; preheat is proactive: it tries to make the reset land somewhere convenient before a limit is ever hit). It would be a genuinely new feature class, not an extension of the existing resume path.

But three things make it a **CONSIDER, not an ADOPT**, and none of them are present in claude-preheat's design because their tool's whole job is to do this:

1. **Cost is real and recurring, and it's not free the way Limit Buster's current behavior is.** claude-preheat's own estimate is "$0.04 at API prices" per ping (README.md:43), and a weekly schedule fires that every scheduled day, plus up to one "chase" ping per day if the schedule mistimes. Limit Buster's existing `budget.ts` already refuses a *resume* that would exceed a cost ceiling; a preheat feature would need the same guard, but the guard alone isn't enough because unlike a resume (triggered by something the user was already doing), a preheat ping is manufactured demand — it exists purely to move the reset clock, so every dollar it spends is 100% attributable to the feature, not to work the user asked for.
2. **It sends a message the user did not ask to send, before any limit was hit.** Limit Buster's existing design (per the brief) is careful about this exact boundary: the trust gate only believes limit text from genuine API-error entries, and the live-panel check refuses to fork a session a VS Code panel still holds open. A preheat feature inverts that carefulness — it originates a new `claude` invocation on a timer with no triggering event from the user at all. That's a bigger step than anything Limit Buster does today and needs correspondingly explicit, granular opt-in (evidenced: claude-preheat ships with schedule.json requiring manual edits and an explicit `preheat apply` command — nothing fires until the user positively configures times, per README.md:20-38).
3. **VS Code extension architecture is a weaker scheduler than what claude-preheat relies on.** claude-preheat's reliability claims ("the task runs only while signed in," wake-from-sleep via RTC timers) all depend on registering with a real OS scheduler (Windows Task Scheduler / launchd, platform.ps1) that persists and can potentially wake the machine. A VS Code extension only runs while VS Code itself is running — there is no OS-level equivalent available to a plain extension, so a preheat feature built as pure extension code could only fire if VS Code happens to be open and awake at the chosen time, which is a materially weaker guarantee than claude-preheat's own (and their own guarantee is already imperfect — they explicitly warn wake timers must be enabled, and on macOS launchd flatly cannot wake a sleeping Mac, per README.md:44 and docs/MAC-BETA.md:52-60). If Limit Buster wanted preheat reliability comparable to claude-preheat's, it would need to register an OS-level task itself (mirroring install.ps1/platform.ps1's approach) — which reintroduces exactly the footprint (profile edits, scheduled tasks/launchd agents) Limit Buster currently avoids by living entirely inside VS Code.

If built, the concrete shape that best fits Limit Buster: an opt-in setting exposing "reset time" (mirroring their `schedule.json` `reset` field, fire = reset − 5h) that, at minimum inside a running VS Code session, fires the same footprint-minimizing ping (see ADOPT #1 below) and shows the user exactly when it will fire and what it costs before enabling it — never on by default, never silent.

### Ranked takeaways

**ADOPT**

1. **The footprint-minimizing `claude` invocation recipe, if Limit Buster ever needs a cheap/invisible probe call.** Exact invocation (confirmed in code at `preheat.ps1:605`, independently re-confirmed by an argv-assertion in `.github/workflows/e2e-mac.ps1`): `-p "hi" --model haiku --no-session-persistence --strict-mcp-config --mcp-config <empty-mcp-config> --output-format json`. `--no-session-persistence` is the flag that (per a code comment, asserted not independently verified against Claude Code's own source) stops the call from writing a transcript into `~/.claude/projects` at all; `--strict-mcp-config` + an empty `mcp-config` JSON file (`{ "mcpServers": {} }`) stops it from loading any of the user's normal MCP servers; `--output-format json` gives back a structured payload including `total_cost_usd` and an `is_error`/`result` field that must be checked even on exit code 0 (their `Test-PingOutput`, `preheat.ps1:516-555`, found in production that "an expired login... exits 0 and still reports the failure inside the payload"). Would touch: any future module that shells out to `claude` for something other than a real resume — e.g. an auth/health check in `src/budget.ts` or a new probe module. Not directly applicable to `resumer.ts`'s `claude --resume <uuid> "Continue..."` call, since that one is *supposed* to create/continue a real transcript.
2. **Filtering non-turn bookkeeping records when judging transcript "activity."** Their `Get-TranscriptActivity` (`preheat.ps1:293-322`) only counts lines matching `"type":"assistant"` or `"type":"user"`, explicitly because Claude Code also appends `attachment`/`away_summary`/`turn_duration`/`stop_hook_summary` records to an open-but-idle session (comment, `preheat.ps1:298-301`) — "the file grew" does not mean the model was called. This is tested directly (test.ps1 titles: "idle-session bookkeeping records do NOT count as activity", "a bumped file mtime does NOT count as activity"). Worth checking whether Limit Buster's own transcript-tailing code (`src/stallWatch.ts`, and wherever `~/.claude/projects/**/<sessionId>.jsonl` growth or mtime is used as a liveness signal) already excludes these record types, or could false-positive on them the same way their file-mtime trap did.
3. **The literal Claude Code usage-limit message format captured in their test fixture**, `"Claude AI usage limit reached|1757062200"` (`test.ps1:184`, in the `result` field of a `-p --output-format json` payload with `is_error:true`). Worth a direct diff against whatever regex `src/parsers/limitParser.ts` currently targets — this may be the exact same format Limit Buster already parses (good, independent confirmation from a different tool/author), or it may reveal that Claude Code emits a differently-shaped limit message in JSON-mode CLI output versus what shows up in an interactive transcript, which would be a gap worth closing.
4. **Anti-chain-loop guard pattern for any scheduled/recurring resume-like action.** Their `Test-RecentPreheatAnchor` (`preheat.ps1:415-442`) exists specifically to stop a self-triggered action from re-triggering itself forever (a chase anchors a window, the next scheduled fire lands inside that window, and must NOT chase again). If Limit Buster's `scheduler.ts` ever grows a "retry on schedule miss" path, this exact class of bug (an automated action perpetually re-arming itself) is worth guarding against the same way.
5. **Distinct, actionable failure-kind notifications.** Their `Send-Toast` (`platform.ps1:443-470`) gives different messages for auth failure ("Claude login expired? run: claude") vs. usage-limit failure ("usage limit already hit, nothing to preheat until it resets") vs. generic failure. Worth checking whether Limit Buster's own resume-failure UX (wherever `resumer.ts`/`extension.ts` reports a failed resume attempt) already distinguishes "your login expired" from "still rate-limited" from "something else broke" — these need genuinely different user actions.

**CONSIDER**

6. **The statusline-tap approach as a second, structured signal source.** `statusline-tap.cjs` (full file read, 82 lines) is a transparent pipe stage installed in front of Claude Code's own `statusLine` command; Claude Code invokes that command on every statusline render and feeds it a JSON payload on stdin containing `rate_limits.five_hour.{utilization or used_percentage, resets_at}` and `rate_limits.seven_day.{...}` (statusline-tap.cjs:27,55-79). This is structured, exact-timestamp data straight from Claude Code itself — no regex parsing of free-text limit messages required, which is a materially different (and possibly more precise) signal than what `limitParser.ts`/`overloadParser.ts` currently extract from transcript text. Their own comment calls it "the only documented machine-readable source of the 5h/weekly usage windows" (statusline-tap.cjs:6-9) — this is their claim, asserted, not verified by us against Anthropic's docs, but it's a claim grounded in a real, working mechanism we can independently confirm exists (Claude Code does support a configurable `statusLine.command` that receives JSON on stdin — confirmed by the code that reads/writes it, `preheat.ps1:1021-1149`). Important limitation: it is push-based and passive — it only updates during an active session's statusline render, so it cannot tell Limit Buster a window has reset while no session is open, meaning it would supplement, not replace, transcript-watching for the "notice a limit hit and schedule a resume" core flow. It would also require Limit Buster to write into the user's `~/.claude/settings.local.json` or `settings.json` (wrapping their existing `statusLine.command`), which is the one place in the whole claude-preheat repo that touches Claude Code's own configuration — worth weighing that footprint against the value of exact reset timestamps. If adopted, their backup/sidecar/restore pattern (`preheat.ps1:1032,1058-1096`) is a solid model for doing it reversibly.
7. **The "preheat" feature itself** — see the dedicated evaluation above. Consider, opt-in only, with the reliability caveat that a pure-VS-Code-extension implementation is strictly weaker than claude-preheat's OS-scheduler-backed one.
8. **A fire-lock / concurrency guard for scheduler actions.** `.fire.lock` (`preheat.ps1:560-581`): PID + timestamp, respected only if the PID is still alive and the lock is under 20 minutes old, otherwise treated as a stale corpse and overwritten. Relevant if `scheduler.ts` could ever have two pending resume timers race (e.g., a manual resume and a scheduled one colliding).

**AVOID**

9. **Registering OS-level scheduled tasks / launchd agents / PowerShell-profile edits as a default behavior.** This is claude-preheat's biggest footprint (full list compiled above under "install.ps1, platform.ps1... — Complete list of changes"): profile edits, `ClaudePreheat-*` Task Scheduler entries, launchd plists, optional `~/.local/bin` shims. Limit Buster currently has none of this — it lives entirely inside the VS Code extension host, which is a real advantage worth preserving (smaller attack surface, nothing to "uninstall" from the OS, no admin/execution-policy edge cases like the ones install.ps1 has to work around, e.g. `install.ps1:189-208`'s execution-policy warning). Only take on this footprint if a preheat-style feature is built AND reliability while VS Code is closed genuinely matters enough to justify it — and even then, make it a distinct, clearly-labeled opt-in step, not something `npm install`/extension-activation does silently the way their README's "paste this into Claude Code and let it install everything" quick-start implicitly encourages.
10. **Silent/automatic cost-incurring pings.** Nothing in Limit Buster today spends money without the user having already been mid-session and hitting a real limit. A preheat feature that fires on a timer, unattended, is a different risk category — even at ~$0.04/ping claude-preheat's own estimate, a forgotten daily schedule adds up, and unlike a resume (clearly tied to "I was working and got cut off"), a preheat ping's entire purpose is speculative. If ever built, it should be exactly as visible and reversible as claude-preheat makes it (a visible schedule, an `apply`-style explicit confirm step, a way to see the next scheduled fire and its estimated cost, an easy off switch) — never inferred or auto-enabled from usage patterns without a confirm step, even though their own `learn` command (`preheat.ps1:823-938`) shows how tempting it is to auto-suggest a schedule from observed rhythm.

### Where Limit Buster is already ahead

- **No OS or shell footprint.** claude-preheat touches the PowerShell profile, Task Scheduler/launchd, and optionally Claude Code's own settings.json; Limit Buster (per the brief's description) does none of this — it's pure extension code plus a VS Code terminal invocation at resume time.
- **A proactive budget guard.** Limit Buster's `budget.ts` estimates a resume's cost and refuses it upfront if it would exceed the limit. claude-preheat reads back actual `total_cost_usd` per ping (`preheat.ps1:543`) but has no equivalent pre-flight refusal — it always fires the scheduled ping regardless of remaining budget; a budget-exhausted preheat still spends money for no benefit (the window can't be usefully anchored if the user is out of budget anyway).
- **A live-session check before forking.** Limit Buster's `liveSessions.ts` uses `claude agents --json` to avoid forking a session a VS Code panel still holds open (issue #6, per the brief). claude-preheat has no directly comparable check — its "does this ping matter" logic (`Test-FreshAnchor`) is about whether a window is already open, not about whether a specific UI surface is mid-conversation with a specific session; the two tools' units of concern differ (window-level vs. session-level), so this isn't a strict win, but Limit Buster's session-level awareness is more granular than anything in claude-preheat.
- **A genuine trust gate on limit text.** Limit Buster only believes limit text from genuine API-error entries, never quoted/pasted conversation text (per the brief). claude-preheat's closest analog, `Test-PingOutput` parsing `is_error`/`result` from its own structured JSON payload, is trustworthy for the same reason (it's reading its own ping's structured output, not free text), but claude-preheat never has to defend against adversarial/pasted text in someone else's transcript the way Limit Buster's resume trigger does, since its own ping's output is the only text it ever parses for a verdict — so this isn't a case where claude-preheat solved a harder problem than us; it's a case where our problem is inherently harder and we've built for it.
