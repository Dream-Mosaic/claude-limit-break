## Claude Code limit-message wording: dated timeline (from claude-auto-retry/CHANGELOG.md)

- **2026-08-16, v0.7.3**: Three renders explicitly quoted as real Claude Code output the parser must distinguish from prose that merely discusses them:
  - Period-terminated: `"Rate limit exceeded. Please try again in 5 hours."`
  - With inline upgrade hint: `"· resets 5:20pm · /upgrade to increase your limits"`
  - Raw API vocabulary: `rate_limit_error` (underscored, API-error-shaped)
  Also documents the *model's own prose* echoing limit language, which is the hard-to-distinguish case: `"⏺ You've hit your usage limit, so try again in 2 minutes."` (CHANGELOG.md:89-91).
- **Unreleased (post-0.7.3, before this digest, i.e. some time between 2026-08-16 and 2026-09-23)**:
  - **Weekly-limit banner gained a calendar date**, not just a clock time: `"You've hit your weekly limit · resets Aug 21 at 3pm (Australia/Brisbane)"` — sourced from "a real Claude Code record surfaced by PR #56's fixture" (CHANGELOG.md:11-22). This is a *format change over time*: weekly limits used to (or were assumed to) reset on a clock-only basis; the dated form broke the existing reset-clause parser, which only recognized "resets 3pm" / "resets at 3:00 PM" / "resets in 3 hours" (a digit immediately after "resets").
  - **New near-limit "wrap up" nudge** (not a limit banner at all): at ~95% of the 5-hour window Claude Code now injects a checkpoint instruction and prints `"⏺ Approaching your 5-hour usage limit — Claude will wrap up the current step."` (CHANGELOG.md:25-39). Described as "a feature-flagged Claude Code behavior with no user-facing switch" — i.e. a silent product change users had to reverse-engineer.
  - **New stream-interruption renders**: Claude Code's response-body byte watchdog now finalizes truncated turns with an `"API Error:"`-prefixed line, one of seven variants, including `"Your computer went to sleep mid-response. The response above may be incomplete."` (CHANGELOG.md:40-58).

**Takeaway for the timeline:** Claude Code's limit/error UI is not stable — new banner shapes (boxed, emoji-presentation, inline-hint, dated weekly reset, wrap-up nudge, sleep/stream-interruption message) kept appearing across roughly two months (Jun–Sep 2026) in claude-auto-retry's own issue history, each requiring a parser update. This directly supports keeping Limit Buster's parsers loose/pattern-based and monitored for drift rather than assuming a fixed format.

## Bug entries from claude-auto-retry/CHANGELOG.md (derived: read directly in CHANGELOG.md, not yet cross-checked against git show — status noted per entry)

### 1. Dated weekly-limit reset not parsed (Unreleased, PR #56 fixture)
- **Symptom:** Weekly-limit banners with a calendar date (`"resets Aug 21 at 3pm (Australia/Brisbane)"`) were not detected at all; the monitor either missed the wait entirely or fell back to a 5-hour default and "burned its retries" while days of limit remained.
- **Root cause:** Reset-clause regex required a digit immediately after "resets" (clock-only forms); a dated reset didn't match, so the scraper saw no reset line next to the limit.
- **Fix:** Dated form added as a recognized reset clause; wait anchors to the calendar day in the banner's own timezone, with year-boundary inference (Dec→Jan) and "reset already in the past ⇒ retry now" handling. (CHANGELOG.md:10-22, Unreleased section — not yet matched to a commit hash.)
- **LB applicability:** Read but not yet checked against `src/parsers/limitParser.ts` — see cross-check section below.

### 2. 95%-window "wrap up" nudge stalls sessions overnight (Unreleased, #78)
- **Symptom:** Claude Code silently wraps up the current step near the 5-hour window edge, ends the turn with no limit banner and no further prompt — an overnight run "parked at 95% until long after the window reset."
- **Root cause:** New Claude Code behavior (feature-flagged, no user-facing switch) that isn't a rate-limit event at all, so limit detectors never fire; it just looks like the session went idle.
- **Fix:** Monitor sends one `continue` at the idle prompt when this specific notice (anchored to shape: message glyph, no user row below it) is seen; not treated as a bounded-retry loop — a notice already answered (by user or by their own nudge) is never re-nudged.
- **LB applicability:** Relevant — Limit Buster only watches for limit/overload messages (per brief). If Claude Code emits this wrap-up notice instead of a real limit banner, Limit Buster's trust gate / parsers would see nothing and would not resume the stalled session. Need to check `src/stallWatch.ts` for any idle-detection independent of the limit parsers.

### 3. Truncated turn (sleep, dropped connection, stalled stream) never resumes (Unreleased)
- **Symptom:** A turn cut off by "computer went to sleep mid-response," a dropped connection, or a stalled stream ends with an `"API Error:"`-prefixed line and the session sits on a half-finished answer indefinitely — Claude Code's own auto-retry only covers thinking-only truncation, not once real content was yielded.
- **Root cause:** Claude Code's byte watchdog aborts and finalizes the stream but doesn't resume it itself past the "thinking-only" stage.
- **Fix:** Monitor detects all seven render variants (suspend, dropped connection, stalled stream, mid-response server error in two forms) anchored on line SHAPE (`API Error:` at column 0 behind at most the message glyph) rather than vocabulary, so quoted explanations don't false-trigger; sends `continue`, bounded by maxRetries since a freshly-woken machine may lack network.
- **LB applicability:** Directly relevant to sleep/wake — see dedicated section below.

### 4. Live banner outranked by reset-shaped prose below it (#73, v0.7.3)
- **Symptom:** A real limit banner is on screen, but a model sentence below it ("The API said to try again in 2 minutes…") or the user's own question matches the reset-time regex too, and being *lower* in a bottom-up scan, wins — turning a 5-hour wait into ~3 minutes. Monitor wakes into the still-live limit and burns `maxRetries` before the real reset.
- **Root cause:** Reset-message scan picked the lowest (freshest-by-position) reset-shaped line without distinguishing a real banner render from prose that merely discusses resets.
- **Fix:** Shape-based veto system: a reset-shaped line stays eligible unless marked as conversation (user input row, sentence punctuation, run-on continuation, message bullet). Any line that *names a limit* is always treated as a render regardless of punctuation — this rule is stated as the fix to three earlier self-inflicted regressions in the same PR that had over-vetoed real banners (period-terminated banners, banners with inline `/upgrade` hint, and `rate_limit_error` API-vocab renders).
- **Known unresolved boundary** (explicitly documented, not a bug they claim to have fixed): prose that itself names a limit ("⏺ You've hit your usage limit, so try again in 2 minutes.") is per-line indistinguishable from a real render and can still outrank a real banner. They chose this direction deliberately because a short fallback wait is "revisited" (self-correcting) while a stale long banner "latches non-correctable."
- **LB applicability:** High — this is exactly the trust-gate problem our brief says Limit Buster already solves architecturally ("Limit text is only believed when it appears in a genuine API-error entry, never in quoted or pasted conversation text"). claude-auto-retry works from a **tmux pane** (rendered terminal text, no structure), so it has no equivalent of a JSONL transcript's structured entries and must reconstruct "is this a real render" from visual shape heuristics alone. Limit Buster parses `~/.claude/projects/**/<sessionId>.jsonl`, which likely has typed entries (api-error vs. assistant-text) — worth confirming our trust gate actually keys off entry *type*, not just text shape, which would make us structurally immune to this whole bug class. Needs confirmation against `src/trust.ts`.

### 5. Reconcile lock double-hold under contention (v0.7.3)
- **Symptom:** Flaky cross-process test suite; two reconcile runs proceeded at once, each arming monitors on the same panes.
- **Root cause:** Stale-lock removal was an unconditional `unlink` even when the lock was already absent (holder released between staleness check and the actual break) — a classic TOCTOU race.
- **Fix:** Identity-checked, skip-when-absent unlink. Measured: ~0.2% double-hold rate before (2/823, 1/1072 contended rounds), 0/6205 after.
- **LB applicability:** Low direct relevance — Limit Buster has one scheduler, not a multi-process lock-file design (per `src/scheduler.ts`, jobs live in a VS Code memento, single extension-host process). Filed as "n/a, different architecture" rather than "we're safe" — worth a quick confirmation there's no analogous race in how multiple VS Code windows on the same machine might both run Limit Buster against the same `~/.claude/projects` tree (not checked this session).

### 6. Secrets exposed via tmux argv (#68, security advisory, v0.7.0)
- **Symptom:** API keys, tokens, connection strings retrievable via a plain `ps` from any local process, for the tmux server's entire multi-day lifetime.
- **Root cause:** Environment forwarded into the auto-created tmux session via `new-session -e KEY=VALUE` (argv), which Linux exposes world-readable via `/proc/<pid>/cmdline`.
- **Fix:** Environment now crosses via a `0600` JSON snapshot file in a `0700` dir; only the path is on the command line.
- **LB applicability:** Low direct relevance — Limit Buster's brief states resumes launch `claude --resume <uuid> "Continue where you left off."` as argv with **no shell and no command string**, so there's no env-injection surface of this shape. Worth a quick confirmation that no secret (API key, token) is ever passed as a VS Code terminal launch argv or env var visible via `/proc` on the resume path — not checked this session, flagged as a targeted follow-up.

### 7. Sessions never reaped, 66 sessions / 16.4 GB in 3 days (#69, v0.7.0)
- **Symptom:** Clean `/exit` never actually destroyed the tmux session; memory/resource leak measured by a reporter over 3 days of real use.
- **Root cause:** Pane tail was an unconditional `; exec $SHELL`, keeping an idle login shell (and the whole process tree) alive forever regardless of how `claude` exited.
- **Fix:** Shell fallback reserved for **non-zero** exits only; clean exit lets tmux reap the session itself.
- **LB applicability:** Low direct relevance in the same shape (Limit Buster doesn't manage a persistent multiplexer session), but the **general pattern — verify a resumed process is watched all the way to completion, not just launched — is exactly what `src/stallWatch.ts` already does** (transcript-growth check catches a resume that silently never started). Whether a *finished* resume terminal is left open/orphaned in VS Code (a much smaller leak than 16GB tmux panes, but a UX annoyance) was not checked this session — worth a look at `src/resumer.ts`.

### 8. Windows tmux failures (#58, #79, and the final "not supported natively" doc, v0.6.2 → Aug 26 2026)
- **Symptom (#58, fixed v0.6.2):** `tmux new-session -e` rejected Windows-carried env var names (`ProgramFiles(x86)`, `=C:` drive pseudo-vars, `!ExitCode`) with `invalid environment variable name`, aborting the whole launch on Git Bash/MSYS2.
- **Fix:** Filter env names to POSIX `[A-Za-z_][A-Za-z0-9_]*` before forwarding; everything else still passes through unchanged via the later snapshot-file mechanism.
- **Symptom (#79, still OPEN as of 2026-09-23):** No native Windows support at all — issue asks for a Windows backend via `psmux` (a tmux-alternative). PR #66 ("feat(windows): add native Windows support") is still OPEN, unmerged.
- **Final state (commit `cb99967`, 2026-08-26):** The maintainer's own README now states plainly: **"Windows: Not supported natively — the tool drives a tmux pane, which Windows does not have. Use WSL2 (Ubuntu), where it works as on Linux."**
- **LB applicability:** High, but as a point of contrast/validation rather than a fix to adopt. Limit Buster's whole design — read a JSONL transcript file, launch via VS Code's own terminal API with argv (no shell, no tmux) — sidesteps this entire bug class by construction: there is no pane to scrape and no multiplexer to be Windows-incompatible with. This is worth stating explicitly in our own docs as a deliberate architectural advantage, since the user's own environment is Windows 11 (per this session's context) and claude-auto-retry is documented as unusable there outside WSL2.

### 9. claude-auto-retry issue #83 (OPEN): two concurrent launches collapse into one shared tmux session
- **Symptom:** Launching `claude` from two separate terminal windows ~18 minutes apart resulted in **both terminals attaching to the same tmux session** — mirrored/identical content, and exiting one pane's session closed both. Confirmed via `ps`/`tmux list-clients`: the second launcher's own `new-session -d` call *did* create a distinct session, but by the time its `attach-session -t <its-own-name>` ran, `tmux list-sessions` showed only the *first* session, and both ttys were clients of it.
- **Root cause:** Not fully diagnosed by the reporter (issue is open, unresolved as of 2026-09-23) — suspected race between `new-session -d` and the session-reaping/`exit-empty` logic added for #69, or a mistarget in how the pane's inner command resolves its own session.
- **Fix:** None yet. Open issue.
- **LB applicability:** This is the closest real-world analogue to "duplicate or forked resumes; typing into the wrong place" the brief asks about, and it is unresolved upstream. Limit Buster's architecture differs in a way that matters here: `src/liveSessions.ts` (per the brief, uses `claude agents --json`) exists specifically to avoid forking a session a VS Code panel still holds open (our issue #6). But issue #6 is itself still OPEN in our own tracker, and its write-up (read this session) documents that Anthropic's own docs warn "If you resume the same session in two terminals without forking, messages from both interleave into one transcript" — i.e. the *underlying* CLI/session hazard claude-auto-retry's #83 is hitting from the tmux side is the same class of hazard our own issue #6 is investigating from the VS Code-panel side. **Not yet resolved in either project.**

### 10. Claude Code UI drift breaks detection: mode-footer moved "esc to interrupt" (#81, OPEN, 2026-09-01)
- **Symptom:** On Claude Code ≥2.1.25x, `esc to interrupt` moved out of the streaming spinner and into a **persistent mode footer** (`⏵⏵ bypass permissions on (shift+tab to cycle) · ← for agents · esc to interrupt · ctrl+t to hide tasks`). claude-auto-retry's `WORKING_PATTERNS`/chrome-stripping logic keyed liveness on that phrase's *old* position; now the bottom-most line of every busy pane matches it, which vetoes trailing-chrome stripping entirely, so the fixed-size detection window fills with footer/widget/input-box noise and a limit banner a few lines up is **never reached at all**. Net effect: "every session limit goes undetected," silently — the monitor logs `Monitor started` and nothing else.
- **Root cause:** Hard dependency on the exact screen position/context of a UI string that Claude Code's own developers moved.
- **Fix:** None yet — open issue with a reproduction script (`probe.mjs`) attached, unresolved as of this digest's date.
- **LB applicability:** Directly relevant as *validation* of Limit Buster's architecture choice, and as a warning. Limit Buster reads the JSONL transcript, not rendered terminal chrome, so a footer/spinner UI reshuffle in the *rendered TUI* cannot affect it the way it affects claude-auto-retry — there is no "chrome" to strip because Limit Buster never looks at chrome. But the underlying lesson generalizes: **Claude Code's wording and structure change over time even in channels Limit Buster does watch** (see the dated timeline above — new banner shapes, the weekly dated-reset format, the wrap-up nudge). `src/parsers/limitParser.ts`'s `LIMIT_HINTS` list is exactly the surface at risk of the same kind of drift, and per our own `docs/PRIOR-ART.md` mutation-testing note (issue #12, referenced there) 10 of 12 hint patterns can already be deleted without a test failing — i.e. our own hint list is under-tested against exactly this kind of silent format drift.

### 11. Consumption warning read as a live limit (PR #85, closed by fix, Sep 2026)
- **Symptom:** Claude Code prints, in the header, while the session is **still working**: `"You've used 91% of your session limit · resets 12:40pm (Europe/Paris) · Run /usage-credits to ask your admin for more"` (observed live on Claude Code 2.1.275, Team plan). claude-auto-retry's `/usage-credits` backstop keyed on two signals — a `/usage-credits` companion and a nearby reset time — both of which this *warning* line carries, even though it names no limit as reached. Consequence: `isRateLimited` returned `true` and **every session that reaches ~90% usage parked itself until the reset, in exactly the window where quota was still usable**, then woke into a session that was never blocked. Reporter's own words: "the offending text is not prose about a limit, it is a real render that means the opposite of what it matches."
- **Root cause:** Detection logic treated "carries the two backstop signals" as sufficient evidence of a live limit, without checking whether the line actually claims the limit was *reached*.
- **Fix:** The warning line is now masked out of the `/usage-credits` backstop's evidence specifically (the main `LIMIT_PATTERNS` path, which does check for an actual "hit/reached" claim, is untouched).
- **LB applicability — CONFIRMED AS A LIVE GAP IN OUR OWN CODE (derived by tracing the regex, not inferred).** Read `src/parsers/limitParser.ts` `LIMIT_HINTS` (lines 49-63) and `RULES` (lines 129-198) directly against this exact banner text:
  - `LIMIT_HINTS` includes `/\b(?:session|usage|weekly|daily|opus|sonnet) limit\b/i` (line 52), which matches the substring `"...your session limit..."` in the 91%-used warning — `looksLikeLimitMessage()` returns `true`.
  - `looksLikeCode()` (the only other gate) does not match ordinary prose — passes.
  - The `clock-reset` rule (line 186) matches `"resets 12:40pm (Europe/Paris)"` directly and resolves to a real future instant.
  - **`detectLimit()` therefore returns a genuine `LimitDetection` for a message that is a usage-percentage *warning*, not a limit-reached notice.**
  - Whether this actually fires in production depends on one thing not verified this session: whether Claude Code writes this specific header/warning text into a transcript JSONL entry with `entry.type !== 'user'` (which `src/transcriptWatcher.ts` line 409 would scan unconditionally) or whether it is purely rendered UI chrome that never reaches the JSONL at all. If it is written (plausible — Limit Buster's own trust-gate design already assumes assistant-authored informational text can appear untagged, per the code comment at transcriptWatcher.ts:406-408), **this is a live false-positive bug**, structurally identical to PR #85's, that would pause a still-working session early. This is the single most concrete, actionable finding of this digest — see "For Limit Buster" below.

### 12. DST-transition wall times resolved inconsistently (v0.6.2, e9a69f5)
- **Symptom:** A date-anchored reset-time roll landing on a DST-transition day: spring-forward (target wall time doesn't exist) made the convergence loop oscillate depending on the *host's* local time, sometimes waking an hour early into a still-live banner (burns `maxRetries`); fall-back (wall time exists twice) had a host-dependent occurrence choice.
- **Fix:** Both cases now resolve deterministically to the **late** side — the skip instant for a nonexistent time, the later occurrence for a repeated one — on the reasoning "waking late by an hour is safe; waking early burns maxRetries into a still-live banner."
- **Related, same release:** a separate DST bug where rolling a stale reset "to tomorrow" was computed as flat `+24h` of milliseconds — one hour short across fall-back, one hour long across spring-forward — recomputed instead on the actual calendar day (commit `2e168f4`).
- **LB applicability — worth comparing to our own known-open issue #10.** Our repo already has **issue #10, OPEN: "A reset time with no zone lands an hour off across a DST change"** — the *same bug class*, already identified but not yet fixed in Limit Buster as of this digest. `src/parsers/limitParser.ts`'s `nextZonedOccurrence()` (lines 210-224) already re-derives the wall clock per calendar day rather than adding a flat 24h — which is the fix claude-auto-retry needed for its "roll to tomorrow" bug (`2e168f4`) — but does **not** appear to special-case which *side* of an ambiguous/nonexistent DST-transition wall-clock reading to prefer the way claude-auto-retry's `e9a69f5` does; `zonedWallClockToInstant()` (lines 110-128) just iterates the offset twice and returns whatever it converges to, with no explicit late-side tiebreak. This is exactly the shape of our own open issue #10 and claude-auto-retry's `e9a69f5` fix is a directly transferable model for closing it (prefer the late/safe side deterministically, don't rely on host-local convergence).

### 13. Off-by-a-day / off-by-24h in timezone offset parsing (multiple issues: #6, #9, #4, #23, #60 across claude-auto-retry's history)
- **Symptom (recurring across at least 4 separate contributor fixes over Apr–Jul 2026):** Reset times in UTC-offset or IANA-zone timezones computed 24 hours (or a large multiple of an hour) off — e.g. PR #4 "correct 24h over-wait for UTC+ timezone rate limit resets", PR #9/issue #6 "off-by-a-day wait in positive-offset timezones", PR #60/CHANGELOG 0.6.1 "timezone off-by-a-day... beyond UTC±12 (e.g. Pacific/Auckland in summer, UTC+13)... made the wait land on the wrong day (~24h too long)".
- **Root cause (final, v0.6.1):** The convergence correction was anchored to a "minimum-magnitude ±12h adjustment" rather than the actual target date, which broke for any banner timezone or host/banner offset split beyond 12 hours.
- **Fix:** Anchor the convergence correction to the target date itself, not a ±12h heuristic; parse the initial guess in host-local time rather than UTC.
- **LB applicability:** This bug class took **five separate community PRs across roughly three months** to fully close upstream, which is itself the headline lesson: timezone/offset arithmetic for "next occurrence of a wall-clock time" is a very easy place to get subtly wrong and re-wrong. Limit Buster's `resolveClockTime()`/`nextZonedOccurrence()` (limitParser.ts:210-306) already do date-anchored, zone-aware resolution (not a ±12h heuristic) for the IANA-zone and local-zone branches — structurally the *already-fixed* shape, not the buggy one — but the `utcBased` branch (numeric UTC offset, e.g. "resets 3pm UTC+13", lines 276-283) still walks forward with a **flat `DAY_MS`** add (`candidate.getTime() + DAY_MS`), justified in a comment as "a numeric UTC offset carries no DST rules of its own, so a flat day is exact." That reasoning holds for the *offset arithmetic itself* (numeric offsets truly have no DST), but it is worth double-checking against Claude Code's actual banner format: does Claude Code ever render a *numeric* UTC-offset banner at all, or only IANA zone names like the ones already seen in this digest ("Europe/Paris", "Australia/Brisbane", "Australia/Sydney")? If it's IANA-only in practice, this branch may be dead code inheriting no real risk; not verified this session.

### 14. `/rate-limit-options` menu keystrokes leaking into the wrong pane (#28, v0.5.0)
- **Symptom:** The interactive menu Claude Code shows on a limit ("Stop and wait" vs. "Upgrade your plan") was driven by sending keystrokes without confirming Claude was actually in the foreground — risking confirming "Upgrade your plan" by accident, or typing into an unrelated pane.
- **Fix:** Require Claude to be in the foreground before driving the menu.
- **LB applicability:** Not directly applicable — Limit Buster never types into a live Claude Code UI at all (per the brief, it opens a *new* terminal with `claude --resume <uuid> "..."` as argv). This class of bug (send-keys into whatever happens to have focus) is inherent to the "watch a pane and type into it" architecture and structurally absent from Limit Buster's argv-based design. Worth stating explicitly as a "we're ahead by construction" point.

## claude-preheat bug entries (from git log, README, SECURITY.md — PowerShell, Windows + macOS beta)

### 15. Microsoft Store PowerShell updates silently break every scheduled task (commit `249deab`, 2026-09-11, found on the maintainer's own machine)
- **Symptom:** A Windows Store update to `pwsh` (7.6.4 → 7.6.6) replaced its versioned `WindowsApps` install folder. Every scheduled task registered before the update kept pointing at the deleted path. **`run-hidden.vbs` exited 0 on a missing exe**, so Windows Task Scheduler's own status stayed green while two scheduled preheat fires and the panel autostart were silently lost. Discovered by dogfooding: "2026-09-10, 7.6.4 -> 7.6.6, on our own machine."
- **Root cause:** (1) Store-installed `pwsh` resolves to a versioned, update-volatile path (`WindowsApps\Microsoft.PowerShell_7.6.4.0_x64__8wekyb3d8bbwe\pwsh.exe`) that a scheduled task had baked in permanently; (2) the launcher shim swallowed the "binary doesn't exist" failure as a success.
- **Fix:** Resolve and bake the stable **App Execution Alias** path (`%LOCALAPPDATA%\Microsoft\WindowsApps\...\pwsh.exe`, survives Store updates) instead of the versioned path, but only after *proving* it actually launches (aliases can be toggled off in Windows Settings); `run-hidden.vbs` now exits 127 on a missing host binary instead of 0; `preheat status` actively checks whether the baked shell path still exists and flags it in red with a fix instruction.
- **LB applicability — HIGH, directly relevant to a Windows-based extension.** Limit Buster is a VS Code extension, so it doesn't bake an absolute `pwsh.exe`/`node.exe` path into a Windows Task Scheduler job the way claude-preheat does — but it does resolve and invoke a `claude` CLI binary path from inside a spawned VS Code terminal (`src/resumer.ts`). The general failure pattern — **a resolved executable path can go stale after an auto-update of the thing being launched, and the failure is silent unless something explicitly checks "does this path still exist" and treats a launch failure as a launch failure** — is worth checking against how Limit Buster resolves the `claude` binary path, especially since our own issue **#16 "Claude path" was opened today (2026-09-23)**, same-day as this digest, suggesting this exact class of problem may already be live in our tracker. Recommend reading issue #16's body directly as a priority follow-up (not done this session — flagged for whoever picks this up next).

### 16. Homebrew `pwsh` resolves to an unrunnable `.NET`-missing binary on macOS (issue #1 / PR #2, 2026-08-26)
- **Symptom:** Every launchd job and both shims got baked with a `pwsh` path that fails at runtapte with `"You must install .NET to run this application."` even though `.NET` and PowerShell were both correctly installed via Homebrew.
- **Root cause:** Inside a running `pwsh` process, `$env:PATH` has `$PSHOME` prepended, so `Get-Command pwsh` resolves to the **bare `$PSHOME` binary** (`/opt/homebrew/Cellar/powershell/7.6.5/libexec/pwsh`, a non-self-contained shim) rather than the user's actual PATH entry, before the `.NET` env vars it needs are set.
- **Fix:** Resolve `pwsh` to the PATH launcher wrapper, not the bare `$PSHOME` binary.
- **LB applicability:** Not directly relevant (Limit Buster is TypeScript/VS Code, not PowerShell), but it's the same *general* lesson as #15 above: **resolving your own runtime's path from inside that runtime is not the same as resolving what a user would actually invoke**, and both of claude-preheat's two platform-specific bugs (Windows Store update, macOS Homebrew) are exactly this. Also documented: the docs command (`brew install --cask powershell`) had gone stale because the cask was removed from homebrew-cask upstream, "not only a stale command... the formula is exactly the install shape that triggers the bug" — a reminder that install instructions in our own docs can rot the same way.

### 17. Sleep/wake: Windows Task Scheduler can wake a sleeping PC, launchd (macOS) cannot
- **Source:** `docs/MAC-BETA.md` ("Known gap: sleep" section) + README.md "Notes" item 3, read directly.
- **Finding:** "Windows Task Scheduler can wake the PC from sleep via RTC wake timers; **launchd cannot wake a sleeping Mac**." On macOS, a scheduled fire that lands while the Mac is asleep simply runs at the next wake — late, "never worse than not having it installed," but the window then anchors at wake time, not the chosen time. Mitigations documented: schedule for times the Mac is normally awake, disable sleep on AC power, and `preheat status` warns when system sleep is enabled. On Windows, the README caveats this further: **"a scheduled fire can only wake the PC if wake timers are enabled in the active power plan — `preheat status` warns when they are off"** — i.e. even on Windows, wake-from-sleep is not automatic; it depends on a power-plan setting the tool has to actively check for and warn about. A **follow-up (chase) ping**, added for the "landed in a running window" case, explicitly **never wakes a sleeping PC at all** — "if the machine is asleep at that minute it is simply skipped" (commit `155adcd`).
- **LB applicability — directly relevant to the "sleep/wake bugs" theme the brief calls out.** Limit Buster's `src/scheduler.ts` (read this session) already avoids the *skew* half of the sleep/wake problem correctly and deliberately: the countdown is "a repeating one-second tick that compares `Date.now()` against each deadline rather than one long `setTimeout`, so suspending or hibernating the machine mid-cooldown cannot skew or swallow the timer" (scheduler.ts:65-67, comment read verbatim). That is a real, working mitigation for "the wait fires late/early after a sleep" — but it is a *different* problem from claude-preheat's, and Limit Buster has no equivalent solution for claude-preheat's problem: **Limit Buster cannot wake a sleeping computer at all.** It runs inside VS Code's extension host; if the machine is asleep at the scheduled resume instant, nothing runs until a human (or something else) wakes the machine, and Limit Buster's countdown simply resumes wherever `Date.now()` lands on the next tick after wake — arguably the same "runs late, never worse than not having it" behavior claude-preheat's docs describe for macOS/launchd, but **Limit Buster has no Windows Task Scheduler equivalent to opt into RTC wake**, and does not warn the user that a scheduled resume during expected sleep hours may simply not happen until the machine is manually woken. Worth adding a warning/status-bar note when a resume is scheduled to land during hours the OS reports the machine will likely be asleep, mirroring claude-preheat's `preheat status` wake-timer warning — see "For Limit Buster" below.

### 18. Cost surprise: preheat pings are cheap but not free, and stack (README.md "Notes" section, read directly)
- **Finding, quoted verbatim (claude-preheat/README.md:43):** *"one short `haiku` prompt — roughly 40k input tokens once Claude Code's own system prompt is counted (about $0.04 at API prices). It counts toward both the 5-hour window and the weekly window, so a preheat is cheap but not free."* The same note documents that a **follow-up ("chase") ping** can be booked automatically when a scheduled preheat lands inside an already-running window — "so that day costs two pings" — bounded to at most one chase per window and never when the next scheduled preheat comes first, with an explicit `"chase": false` opt-out in `schedule.json`.
- **Not a bug in the classic sense** — this is a disclosed, deliberate cost, not a defect — but it is exactly the "cost surprises" theme the brief asks about, and the design response (state the $ cost plainly in the docs, bound the automatic multiplication, give an opt-out) is the relevant artifact.
- **LB applicability:** Limit Buster's cost concern is structurally different (per `src/budget.ts`, read this session): it is not "does our own tool's action cost money" (Limit Buster never sends a paid message on its own initiative outside the one resume) but "will the **resume itself** cost more than expected because a cold prompt cache forces the whole session history to be reprocessed." Limit Buster is already ahead here — `budget.ts`'s `checkBudget()`/`estimateResumeTokens()` explicitly guards against exactly this, citing a real measured case: an 11.2 MB session with a byte-based estimate of 2,007,179 tokens vs. an actual largest-ever cache-creation of 407,570 tokens, i.e. "the guard refused a resume costing a quarter of what it claimed." Worth noting as a place Limit Buster is **already ahead** of both prior-art projects (neither claude-auto-retry nor claude-preheat has an equivalent pre-flight cost estimate/guard for the action they take — claude-preheat instead controls cost by using the cheapest model, `haiku`, and disclosing the number rather than estimating and refusing).

### 19. Claude Code shipped a *native* auto-continue-at-reset feature mid-2026 — and the two prior-art repos disagree about its scope
- **Source A (claude-auto-retry, commit `9ae90da`, 2026-08-13, README banner read directly):** *"The Claude **Desktop app** now does this natively — an 'Auto-continue when limits reset' checkbox (confirmed in the wild, linking `anthropics/claude-code#35744`). The **CLI still doesn't have it** — that's the gap this tool covers today."* This banner is **still present verbatim** in claude-auto-retry's README as of its latest commit (`cb99967`, 2026-08-26) — i.e. as of the *last* commit in their history, they still believe the CLI lacks native auto-continue.
- **Source B (claude-preheat, commit `91ae26a`, 2026-08-19, v0.3.0 commit message + README read directly):** *"Claude Code CLI v2.1.234 ships native auto-continue at usage-limit reset (default on, `/config` 'Continue automatically at usage limit'), which covers the stay-at-the-keyboard case in-process and better."* claude-preheat's maintainer **retired their own cross-window "relay" auto-resume feature specifically because of this**, stating in `SECURITY.md`/README that competing with a native platform feature wasn't worth it.
- **These two claims contradict each other** (Desktop-only vs. CLI-too) and were made only 6 days apart (Aug 13 vs. Aug 19, 2026), with claude-auto-retry's repo never updating its banner afterward even though its own later commits (through Aug 26) post-date claude-preheat's claim. **Not independently verified against Anthropic's own changelog or docs this session** — flagged as a genuine open question rather than resolved either way, per the brief's "derive, don't infer" rule.
- **LB applicability — this is the single highest-priority open question this digest surfaces.** If Claude Code's CLI genuinely gained a native, **default-on** "Continue automatically at usage limit" setting at some point in its 2.1.x line, then **every session Limit Buster watches may already be trying to auto-continue itself** the moment its own limit resets — in the *same* terminal/process the limit hit in, if that process is still alive (exactly the scenario our own issue #6 investigates for VS Code panel sessions, and exactly the shape of claude-auto-retry's unresolved issue #83). This was **not found anywhere in Limit Buster's own `src/`, `docs/`, or issue tracker** (checked: grepped `docs/`, `src/` for "auto-continue", "2.1.234", "35744" — zero matches; also checked issue #6's full body — no mention). This needs a direct check against a current Claude Code install (`/config` → look for "Continue automatically at usage limit") before anything else in this digest, because if true it changes what "duplicate resume" risk looks like for Limit Buster: the risk may not be "two terminals both showing a limit" but "the original terminal auto-continues on its own the instant Limit Buster's countdown also fires, doubling up every single resume."

## For Limit Buster

Ranked by how directly actionable each is. Each item names its evidence and the file it would touch.

### Adopt

1. **Verify, urgently, whether Claude Code's CLI now has a native "Continue automatically at usage limit" setting, and if so, teach Limit Buster to detect it and not double-resume.** Evidence: bug entry #19 above — two prior-art repos make contradictory claims about this (claude-auto-retry says CLI still lacks it as of its last commit 2026-08-26; claude-preheat says CLI v2.1.234 shipped it 2026-08-19, and retired their own competing feature because of it). Neither claim was independently confirmed this session. If claude-preheat is right, this is a first-class duplicate-resume risk on top of the panel-liveness one our issue #6 already tracks. Files: `src/liveSessions.ts` (the existing live-session check would need to also account for "this session's own process may auto-continue itself"), `src/scheduler.ts`/`src/resumer.ts`. Action: check a real Claude Code install's `/config` menu, and check whether `~/.claude/sessions/<pid>.json` (already used by our issue #6 investigation) or the transcript itself records anything indicating an in-process auto-continue occurred, before scheduling an external resume.

2. **Guard against a usage-percentage *warning* being read as a limit-*reached* notice.** Evidence: bug entry #11 — claude-auto-retry's PR #85 hit exactly this in production ("You've used 91% of your session limit · resets 12:40pm (Europe/Paris) · Run /usage-credits to ask your admin for more" parked a still-working session), and tracing Limit Buster's own `LIMIT_HINTS` (`/\b(?:session|usage|weekly|daily|opus|sonnet) limit\b/i`) and `clock-reset` rule against that exact string shows `detectLimit()` would return a genuine (false) detection today. File: `src/parsers/limitParser.ts`. Fix shape to mirror: require the matched text to claim the limit was *reached* (hit/used up/exceeded), not merely *approached* — e.g. a veto for "X% of your ... limit" / "used N%" phrasing the way PR #85 masked its backstop's evidence, or require `looksLikeLimitMessage` to be satisfied by a "reached" phrase specifically when a bare "session/usage limit" phrase co-occurs with a percentage. Needs one more check first (not done this session): whether Claude Code actually writes this banner text into a JSONL entry with `type !== 'user'`, since `src/transcriptWatcher.ts:409` is the only thing standing between this regex and a real false resume.

3. **Add a stream-interruption / "computer went to sleep mid-response" detector.** Evidence: bug entry #3 — claude-auto-retry's newest feature (merged PR #77, 2026-08-17) handles seven render variants of a turn Claude Code's own byte-watchdog finalized after a suspend, dropped connection, or stalled stream, including the literal string *"Your computer went to sleep mid-response. The response above may be incomplete."* Traced against Limit Buster's `src/parsers/overloadParser.ts`: none of its five `RULES` (api-error-status, overloaded, server-error, connection-error, timeout) match this wording, so a session interrupted this way currently gets no automatic handling from Limit Buster at all — it just sits on a half-finished answer. This is squarely inside the "sleep/wake bugs" theme the brief calls out, and inside Limit Buster's own stated scope (usage-limit and overload messages). File: `src/parsers/overloadParser.ts` — add a rule anchored on `API Error:` at column-0-equivalent (start of the JSONL string, since there's no "chrome" to worry about the way tmux scraping does) matching the sleep/dropped-connection/stalled-stream wording family.

4. **Close our own open issue #10 (DST off-by-an-hour) using claude-auto-retry's already-proven fix shape.** Evidence: bug entry #12 — claude-auto-retry's `e9a69f5` resolves ambiguous/nonexistent DST-transition wall-clock readings deterministically to the *late* side (safe: waking late costs nothing, waking early burns retries into a still-live limit), after their own multi-revision history of getting the host-dependent convergence wrong. Limit Buster's `nextZonedOccurrence()`/`zonedWallClockToInstant()` (`src/parsers/limitParser.ts:110-224`) already do date-anchored resolution but have no explicit late-side tiebreak for a transition-day reading. Same file our own issue #10 already points at.

5. **Warn the user when a scheduled resume is likely to land while the machine is asleep, the way `preheat status` warns about disabled Windows wake timers.** Evidence: bug entry #17 — claude-preheat explicitly checks and surfaces "wake timers are off" as a status warning on Windows, and documents the macOS/launchd gap ("launchd cannot wake a sleeping Mac") as a known, disclosed limitation rather than a silent one. Limit Buster's `scheduler.ts` already handles the *skew* half of sleep/wake correctly (re-derives from `Date.now()` on every tick rather than trusting `setTimeout`), but has no equivalent of "this extension cannot wake a sleeping computer at all, and here's what that means for a countdown scheduled for 3am." File: `src/statusBar.ts` (surfacing) + wherever the scheduled resume time is set, to check it against expected-sleep hours if that's knowable, or at minimum document the limitation the way claude-preheat does.

### Consider

6. **Mutation-test (or otherwise harden) `LIMIT_HINTS`/`overloadParser` `RULES` against Claude Code wording drift as a standing practice, not a one-time fix.** Evidence: the dated timeline at the top of this file shows Claude Code's limit/error UI changed shape repeatedly over roughly two months in claude-auto-retry's own history (boxed banners, emoji-presentation warning glyphs, inline-hint banners, a weekly banner gaining a calendar date, a wholly new "wrap up" nudge, a wholly new stream-interruption error family) — and claude-auto-retry's open issue #81 shows a *recent* Claude Code UI change (≥2.1.25x moving "esc to interrupt" into a persistent footer) currently breaks their detection entirely, unresolved as of this digest. Our own `docs/PRIOR-ART.md` already records that 10 of 12 `LIMIT_HINTS` entries can be deleted without a test failing (issue #12 referenced there) — i.e. we already know our hint list is under-tested against exactly the kind of drift this history shows keeps happening. This isn't a specific fix, it's a standing-maintenance argument: budget for periodic re-verification against a current Claude Code install.

7. **Consider whether Limit Buster's live-panel check (`src/liveSessions.ts`, our issue #6) needs to reason about it differently now that at least one prior-art maintainer believes native CLI auto-continue exists.** Bundled with item 1 above; listed separately because it's a design question (what should Limit Buster do if it detects the original process is about to auto-continue itself — skip its own resume? race it harmlessly since both send an equivalent prompt?) rather than a pure bug fix.

8. **Document, in our own docs, the deliberate architectural advantages this digest surfaces, so they don't get silently regressed.** Two are worth stating explicitly rather than leaving implicit: (a) reading a structured JSONL transcript with typed entries (`isRateLimitEntry`/`isApiErrorEntry` in `src/transcriptWatcher.ts`) makes Limit Buster structurally immune to the entire class of "is this line a real render or a quotation/prose-about-it" shape-guessing bugs that consumed multiple claude-auto-retry releases (#63, #73, and the three self-inflicted regressions documented inside #73's own fix) — because claude-auto-retry has to guess this from *rendered tmux pane text* with no structure at all, while Limit Buster gets a `type`/`isApiErrorMessage`/`apiErrorStatus` field for free; (b) launching via VS Code's terminal API with argv (no shell, no tmux, no pane) is structurally immune to the Windows-unsupported problem (claude-auto-retry: "Windows: Not supported natively... Use WSL2"), the tmux-session-collision problem (claude-auto-retry issue #83, open), and the send-keys-into-wrong-pane problem (claude-auto-retry issue #28/PR fix) all at once.

9. **`src/budget.ts`'s pre-flight cost guard is already ahead of both prior-art projects** — neither claude-auto-retry nor claude-preheat estimates and refuses an expensive resume/action the way `checkBudget()`/`estimateResumeTokens()` does (claude-preheat instead controls cost by using the cheapest model and disclosing the number; claude-auto-retry doesn't address resume cost at all). No action needed — recorded so this strength isn't accidentally traded away in a future refactor.

### Avoid

10. **Do not adopt a tmux-pane-scraping (or any rendered-terminal-scraping) architecture, even partially, for any future feature.** Evidence: the majority of claude-auto-retry's 143 commits and its open issues (#81, #83, and the whole "chrome-aware detection" subsystem added in v0.6.0) exist to fight problems that are inherent to scraping rendered terminal output rather than reading structured data — problems Limit Buster's JSONL-based design doesn't have. If a future feature is tempted to also watch a VS Code terminal's rendered output (e.g. for richer status), treat that as reintroducing this entire bug class.

11. **Do not bake an absolute, version-specific path to an auto-updating binary into any persisted job/config without a "does this still exist" check at fire time.** Evidence: bug entries #15 (Windows Store `pwsh` update silently orphaned every scheduled task) and #16 (macOS Homebrew `pwsh` path resolution bug) — both were real, dogfooded production incidents, not theoretical. Limit Buster doesn't currently persist an absolute binary path the way claude-preheat's Task Scheduler jobs do, but if any future feature resolves and caches a `claude` CLI binary path (our own issue #16, opened today, may already be about exactly this — not read in full this session, flagged as the first thing to check), it should re-validate the path at use time rather than trusting a cached resolution, and treat "the path doesn't exist" as a loud failure, not a silent no-op (claude-auto-retry's own `run-hidden.vbs exit 0 on missing exe` bug is the cautionary example of getting this wrong).
